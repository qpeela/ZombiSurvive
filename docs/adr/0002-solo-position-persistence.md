# ADR 0002 — сохранение позиции одиночного мира

Статус: принято для T013. Дата: 24 октября 2026 года.

## Проблема

Перезапуск сервера теряет позицию и идентичность solo-персонажа. Архитектура
предусматривает SQLite у хоста, но адаптер хранения ещё не реализован.
Нужно сохранить один мир без изменения сетевого протокола и общего ядра.

## Варианты

- JSON с временным файлом и rename: прост для позиции, но требует отдельной
  реализации блокировки владельца и перехода на SQLite для последующих систем.
- SQLite через внешнюю библиотеку: соответствует архитектуре, добавляет зависимость.
- Встроенный node:sqlite из выбранного Node 24: тот же формат SQLite, без зависимости;
  синхронные короткие записи могут задерживать event loop при медленном диске.

## Решение

Использовать DatabaseSync в серверном SoloWorldStore. Схема user_version=1 хранит
один worldId/playerId, seed/generatorVersion и xMeters/yMeters. Доменное состояние,
сетевой snapshot и запись БД преобразуются явно. Клиент и packages не знают о БД.

Загрузка выполняется до открытия listener. Проверять совместимость схемы и
генератора, идентификаторы и допустимую свободную позицию. Ошибка не создаёт
замену прежнего мира. Версия 0 допускается только для пустой БД;
автоматических миграций прежних сохранений пока нет.

Отдельный таймер раз в секунду выполняет короткий атомарный UPDATE вне step().
DELETE journal, synchronous=FULL и EXCLUSIVE locking удерживают одного владельца
между commit. При штатном shutdown сначала останавливаются шаги и таймер,
затем сохраняется позиция, отключаются клиенты и закрывается БД.
При ошибке записи хост останавливается с ненулевым кодом.

Путь по умолчанию .local/solo.sqlite вычисляется от серверного модуля;
WORLD_SAVE_PATH задаёт абсолютный путь. Кооператив пока остаётся в памяти
и не открывает solo-файл. Схема и генератор имеют независимые версии.

## Последствия и проверка

После аварии возможен откат к последнему commit: обычно до секунды, при задержке
event loop — дольше. Stamina, намерения и ack не сохраняются. Для увеличения объёма
записей потребуются измерения задержки и решение о worker; в T013 их нет.
Автоматические бэкапы и миграции новых систем выполняются отдельно.

Unit-тесты проверяют round-trip, ошибки, блокировку, атомарность и lifecycle;
Chromium/процессы проверяют restart, SIGKILL, другой порт/профиль/cwd и отказ записи.
Прежние smoke-сценарии используют временные файлы и production entrypoint.

# ADR 0003 — устойчивое местонахождение предмета

Дата: 29 октября 2026 года. Статус: принято в T026.

## Контекст

В игре есть один бинт starter-bandage: на земле или в контейнере игрока.
T015/T016 подтверждали перенос в памяти, поэтому рестарт возвращал предмет на землю.
T026 сохраняет существующий лут и его ячейку без изменения ассортимента и сетевого DTO.

## Решение

SQLite user_version=3 добавляет к единственной solo_world колонку item_location.
Это ограниченная JSON-запись единственного местонахождения: ground с мировой
позицией либо container с playerId и ячейкой. Конвертер saved-item проверяет
неизвестное значение, размер записи, существующий ID/тип, начальную позицию,
единственного владельца и допустимый footprint. Неизвестные/повреждённые данные
останавливают загрузку; восстановление не создаёт дополнительный предмет.

Миграции v1/v2 выполняются в прежней EXCLUSIVE-транзакции вместе с проверкой
мира/профиля/предмета. Старые схемы не хранили лут: при первой миграции создаётся
один прежний бинт на земле. ID мира/игрока, позиция, имя и ревизия сохраняются.
Для v3 повторной инициализации нет. Ошибка откатывает и схему, и данные.

LocalWorldPickup готовит переход на серверном шаге и сохраняет его невидимым
в pendingSave. Room забирает его один раз; setImmediate после завершения шага
выполняет UPDATE item_location. SQLite DELETE journal, synchronous=FULL и
единственный владелец БД сохраняют атомарность всех полей местонахождения.
Только после commit результат помечается готовым и публикуется на следующем шаге.
Пока запись не закончена, команды ограниченно копятся по сессиям и затем снова
проверяются по актуальному состоянию. Повторные pickup/move не создают копий.

Ошибка записи останавливает шаги и хост с ненулевым кодом без подтверждения
несохранённого переноса. При остановке до commit клиент видел старое состояние;
commit без доставки подтверждения безопасно восстанавливается при retry.
Периодическое сохранение позиции не заменяет подтверждение записи предмета.

## Ограничения и последствия

JSON-колонка соответствует единственному текущему экземпляру. Несколько предметов,
оружие из сетки и иные типы потребуют отдельной миграции, а не неявного расширения.
Историю лута старой работающей версии v1/v2 восстановить невозможно: её не было в БД.
Кооператив этот solo-файл не открывает и сохраняет прежний режим в памяти.
Экипировка, HP, cooldown, зомби и тела не входят в T026.
Синхронный fsync может задерживать event loop; workers и замеры нагрузки отложены.

## Расширение в T027 — SQLite v4

item_location теперь содержит массив пяти местонахождений: прежний бинт
и по одному экземпляру club/knife/crowbar/axe с ID `<playerId>:<kind>`.
Оружие находится только в container или единственном hands того же владельца.
Каждый footprint оружия 1 × 1; массы 400/100/600/800 г позволяют сохранить
контейнер 4 × 3/2000 г вместе с бинтом. Эти прототипные параметры в content,
баланс боя не меняется.

Миграция v3 сначала валидирует старый бинт и сохраняет его ячейку. Четыре
экземпляра размещаются в свободных ячейках; если места/массы недостаточно,
транзакция откатывается целиком. Версии v1/v2 проходят прежние ступени в той же
транзакции. v4 больше не выдаёт набор; missing/duplicate/foreign ID, пересечение,
два hands и неверный kind останавливают загрузку без сброса.

Вся сетка и руки меняются одним UPDATE/FULL commit, прежний порядок
pendingSave → commit вне шага → публикация сохранён. Атака до commit использует
прежние руки, после commit — новый слот. Смена не обнуляет cooldown процесса.
HP/cooldown и мировой оружейный лут остаются задачами T029/T028.

# Организация разработки агентами

Статус: предложенный процесс. Агенты разработки ещё не запущены.
Основа требований: [GAME_DESIGN.md](../GAME_DESIGN.md).
Архитектура: [ARCHITECTURE.md](ARCHITECTURE.md). Кодстайл: [CODE_STYLE.md](CODE_STYLE.md).

## 1. Управление работой

Пользователь определяет приоритеты и оценивает игровой опыт.
Ведущий агент в основном чате отвечает за планирование, контракты,
интеграцию, проверку результата и актуальность документации.
Подагенты получают ограниченные задачи с явными границами изменений.

Для крупного этапа достаточно ведущего и двух-трёх исполнителей одновременно.
Для выбранного пользователем экономного ручного режима выполняем одну небольшую
задачу одним агентом за запуск. Очередь — [BACKLOG.md](BACKLOG.md),
текущее состояние — [PROGRESS.md](PROGRESS.md).
Дополнительных специалистов подключаем по необходимости при поручении
параллельной работы. Число ролей не означает число постоянно работающих агентов.

В Codex можно поручать независимые части задачи подагентам из основного чата.
Ведущий собирает их результаты. Отдельные чаты для каждого исполнителя
не обязательны. Подагенты расходуют дополнительные токены, поэтому
параллельность выбираем по независимости задач и бюджету.

Источник возможностей: [официальная документация Codex о подагентах](https://developers.openai.com/codex/agent-configuration/subagents).

## 2. Роли и владение кодом

Пути ниже описывают будущую структуру; кодовых пакетов пока нет.

| Роль                | Ответственность                                                  | Область записи                                                                                           |
| ------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Ведущий             | Архитектура, контракты, окружение, зависимости, интеграция       | Корневые настройки, packages/domain, packages/protocol, docs; интеграционные изменения после координации |
| Клиент              | Phaser, камера, ввод, HUD, инвентарь и отображение состояния     | apps/client                                                                                              |
| Симуляция           | Движение, столкновения, бой, потребности, AI и правила инвентаря | packages/simulation                                                                                      |
| Сервер              | Подключения, выполнение команд, доступ, БД и восстановление мира | apps/server                                                                                              |
| Генерация и контент | Чанки, seed, локации, описания предметов                         | packages/worldgen или packages/content — назначаются отдельно                                            |
| QA                  | Проверки правил и интеграции, воспроизведение ошибок             | Только заранее назначенные тестовые файлы                                                                |

Ревьюер получает завершённый diff и работает без изменения файлов.
Автор модуля может писать тесты своего изменения; QA проверяет независимые
сценарии и границы систем, не дублируя работу автора.

Одному файлу назначается один активный автор, включая тесты.
Ведущий не редактирует файлы исполнителя, пока задача не завершена
или владение явно не передано.

## 3. Сначала общий контракт

Перед параллельной реализацией ведущий создаёт минимальный каркас и фиксирует:

- систему координат, единицы расстояния и времени;
- идентификаторы мира, персонажа, предмета и чанка;
- команды ввода, подтверждения сервера и видимое клиенту состояние;
- интерфейс шага симуляции и источник времени;
- формат генерации чанка, препятствий и версии генератора;
- интерфейс сохранения и восстановления.

Исполнители не меняют общий контракт самостоятельно. Если его недостаточно,
они описывают необходимое изменение ведущему. После согласования ведущий
обновляет контракт и сообщает затронутым исполнителям.

## 4. Карточка задачи

Каждое поручение содержит:

```text
Цель: проверяемое поведение игрока или системы.
Контекст: нужные разделы GAME_DESIGN.md, ARCHITECTURE.md, CODE_STYLE.md и существующие контракты.
Владение: точный список разрешённых файлов/каталогов.
Входы и выходы: интерфейсы и зависимости от других задач.
Ограничения: что не входит в этот этап.
Готовность: конкретные сценарии, которые должны работать.
Проверки: необходимые тесты и способ ручной проверки.
Отчёт: изменения, выполненные проверки, ограничения и блокеры.
```

Обязательные инструкции исполнителю:

- Ты работаешь не один; не отменяй чужие изменения.
- Меняй только назначенную область и учитывай соседние изменения.
- Не добавляй игровые системы вне задачи.
- Не меняй общие зависимости, lockfile и контракты без координации.
- Сообщай о блокерах сразу; не подменяй недостающий контракт своей версией.
- Для frontend JS/TS применяй frontend-code-style; для React/FSD,
  если они появятся, также react-fsd-code-style.

При запуске без истории ведущий явно передаёт все необходимые требования,
пути, контракты и абсолютные пути к применимым скиллам.

## 5. Первая последовательность работ

1. **Ведущий:** каркас клиента и сервера, команды запуска, общие контракты.
2. **Параллельно после фиксации контрактов:**
   - клиент: сцена, камера, WASD, мышь и отображение состояния;
   - симуляция: движение, столкновения, спринт и скрытность;
   - сервер: подключение одного игрока, игровой цикл и сохранение позиции.
3. **Генерация:** первый процедурный участок по согласованному интерфейсу.
   При нехватке бюджета эту часть делает ведущий или освободившийся исполнитель.
4. **Ведущий:** соединяет модули и устраняет интеграционные проблемы.
5. **QA:** проверяет движение, препятствия, повторный вход и сохранение.
6. **Следующий игровой этап:** лут, сетка инвентаря, зомби и бой;
   новую декомпозицию делаем по реальным зависимостям готового кода.

Результат первого этапа: браузер подключается к серверу, персонаж перемещается
по процедурной местности и возвращается в сохранённую позицию после входа.

## 6. Общий рабочий каталог и изоляция

В текущем чате подагенты работают с общими файлами. Сам факт запуска
подагента не создаёт отдельную ветку или изолированную копию.
Поэтому сначала используем непересекающееся владение файлами.
Установку зависимостей и изменение корневых настроек выполняет ведущий.

Если задачи потребуют пересекающихся изменений, после появления Git-репозитория
можно использовать отдельные worktree. Назначение checkout, исходную ревизию
и способ переноса результата ведущий указывает явно. Результаты интегрируются
последовательно и проверяются вместе.

## 7. Готовность и проверка

Задача завершена, когда:

- заявленное поведение реализовано в рамках требований;
- пройдены проверка типов, сборка и релевантные тесты;
- изменения совместимы с общими контрактами;
- выполнена проверка в общей сборке;
- опубликован отдельный PR в GitHub, CI прошёл на актуальном коммите;
- оставшиеся ограничения описаны явно.

Порядок локальных проверок, публикации и контроля CI — [PR_PROCESS.md](PR_PROCESS.md).
После зелёного CI задача получает IN_REVIEW, после слияния — DONE.
Слияние не выполняем без отдельного поручения; зависимые задачи ждут его.

Отчёт исполнителя — промежуточный результат. Ведущий отвечает за финальную
проверку всей игры. Проверки отдельных модулей не заменяют запуск браузерного
сценария. После каждого игрового этапа пользователь получает запускаемую
версию, инструкцию запуска и короткий список изменений.

## 8. Разработка и PR-ревью

Предоставленные пользователем PR Review Instructions применяются именно
к frontend-ревью относительно origin/main: шесть отдельных областей,
backend intentionally out of scope. Они не ограничивают разработку серверной
части игры. Проверки серверной симуляции, хранения и восстановления входят
в разработку и интеграционное тестирование; для отдельного backend-аудита
нужна самостоятельная задача с явно заданным scope.

Шесть ревьюеров не запускаются на каждое небольшое изменение автоматически.
При выполнении формального frontend PR-ревью состав и формат соответствуют
инструкциям пользователя.

## 9. Пример поручения на запуск

В выбранном ежедневном ручном режиме достаточно:

```text
Сделай следующую задачу из docs/BACKLOG.md.
Прочитай docs/PROGRESS.md. Выполни одну задачу одним агентом,
проверь результат, создай PR в GitHub, проверь CI и обнови прогресс.
Следующую задачу не начинай.
```

Для отдельного поручения целого этапа с параллельной реализацией:

```text
Начни первый технический прототип по GAME_DESIGN.md и docs/AGENT_WORKFLOW.md.
Ты ведущий. Сначала создай каркас и общие контракты, затем делегируй
независимые части подагентам: клиент, симуляция, сервер.
Не более трёх исполнителей одновременно. Назначь непересекающиеся файлы.
Собери результаты и проверь игру в браузере, включая сохранение позиции.
В конце дай команды запуска, результаты проверок и известные ограничения.
```

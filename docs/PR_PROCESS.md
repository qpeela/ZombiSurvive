# Завершение задач через GitHub PR

Требование пользователя: каждая задача разработки завершается отдельным PR
с запуском тестов и остальных необходимых проверок.
Репозиторий: https://github.com/qpeela/ZombiSurvive.
Этот документ описывает процесс; текущая запись правил не запускает T001.

## 1. Начало задачи

- Проверить рабочее дерево и сохранить чужие изменения нетронутыми.
- Проверить актуальный origin/main и состояние PR, от которых зависит задача.
- Выполнять новую задачу в отдельной ветке, например task/t001-project-scaffold.
- Если рабочее дерево содержит постороннюю работу, использовать изолированную
  копию или worktree, не перенося её в PR без необходимости.
- Если необходимый предыдущий PR ещё не слит, записать ожидание зависимости.
  Продолжение незавершённой задачи использует её существующие ветку и PR.

## 2. Проверки перед PR

Для кодовых изменений запускать настроенные проверки проекта:

- lint и проверку форматирования;
- проверку типов;
- существующий автоматизированный набор тестов;
- сборку клиента и сервера;
- релевантные интеграционные проверки и браузерные сценарии.

Тесты нового поведения должны проверять существенные правила и ошибки,
а не повторять реализацию. Для изменения только документации проверять
Markdown, ссылки и git diff; отсутствие runtime-тестов объяснить в PR.
Неприменимые или недоступные проверки явно отмечать, не выдавать их за пройденные.

Перед фиксацией изменений проверить diff и git diff --check.
В коммит включать только файлы задачи. Внести актуальный прогресс и результаты
проверок. Не добавлять посторонние изменения, секреты или локальные данные игры.

## 3. Публикация и CI

1. Создать коммит и отправить ветку в origin.
2. Создать PR в main с ID задачи, описанием поведения, scope и проверок.
3. Прикрепить созданный PR к текущему чату средствами Codex.
4. Проверить, что GitHub Actions действительно запустился на актуальном коммите.
5. Дождаться результата обязательных проверок. Ошибки изменения исправить
   в этой же ветке и проверить CI нового коммита.
6. Вернуть ссылку на PR, результат проверок и известные ограничения.

Если создание PR или CI недоступно, явно описать препятствие и сохранить
состояние для продолжения. Задачу не считать полностью завершённой.
Истечение времени ожидания не означает успех CI. Если CI ещё выполняется,
указать статус ожидания и продолжить проверку результата при следующем запуске.

GitHub CLI не обнаружен в текущем PATH при проверке 13 октября 2026 года.
В S001 публикация PR проверена через авторизованный встроенный браузер GitHub.
Для проверки публичного CI доступен GitHub API без токена. CLI необязателен.
Не сохранять токены в репозитории.

## 4. Статусы и зависимости

- IN_PROGRESS: реализация или исправления ещё идут.
- CI_PENDING: PR открыт, результат обязательного CI ещё не подтверждён.
- IN_REVIEW: PR открыт, локальные и обязательные CI-проверки прошли.
- DONE: PR слит в main, подтверждено состояние зависимостей.
- BLOCKED: есть конкретное внешнее препятствие.
- PAUSED: пользователь явно отложил задачу; она возобновляется только по отдельному
  поручению и не блокирует независимую очередь.

Разработка и публикация результата задачи завершены в IN_REVIEW.
Слияние выполняется пользователем или по его отдельному поручению.
Автоматическое слияние не включено этим требованием о создании PR.
Следующая зависимая задача начинается от актуального main после слияния.

Номер PR и его актуальный статус хранить в PROGRESS.md. Ссылку можно записать
после создания PR отдельным небольшим коммитом в той же ветке, затем проверить
CI актуального коммита. При новом запуске сверять состояние с GitHub.

## 5. Первая задача

В S001 добавлен общий GitHub Actions workflow на pull_request в main.
T001 расширяет его проверками игровых приложений:
воспроизводимая установка зависимостей, lint/форматирование, typecheck,
автоматизированные smoke-проверки и build. Проверка запуска клиента и доступности
сервера должна подтверждать работоспособность каркаса.
Использовать согласованные команды проекта и совместимые версии инструментов.

По мере появления логики добавлять содержательные unit- и интеграционные тесты.
Обязательное формальное frontend PR-ревью, когда оно поручено, выполняется
по пользовательским PR Review Instructions с шестью областями.
Тестирование серверной части входит в разработку; backend остаётся вне scope
именно этого frontend-ревью.

# Правила кода

Обязательны для нового кода всех агентов. Настройки formatter и linter находятся
в корне и общие для всех пакетов. Архитектурные границы — [ARCHITECTURE.md](ARCHITECTURE.md).
На frontend дополнительно применяется пользовательский frontend-code-style;
для React/FSD, если они появятся, также react-fsd-code-style.

## 1. Форматирование

Prettier отвечает за форматирование; ESLint — за качество и ошибки.
eslint-config-prettier отключает конфликтующие правила. Prettier запускается
отдельно, не через eslint-plugin-prettier.

| Настройка                 | Значение                                   |
| ------------------------- | ------------------------------------------ |
| JS/TS/CSS отступ          | 4 пробела                                  |
| JSON/YAML/Markdown отступ | 2 пробела                                  |
| Кавычки JS/TS             | Одинарные                                  |
| Точка с запятой           | Обязательна                                |
| trailingComma             | all                                        |
| arrowParens               | avoid                                      |
| printWidth                | 100, ориентир formatter, не жёсткий предел |
| Концы строк               | LF, финальный перевод строки               |

.editorconfig согласован с Prettier. Не добавлять форматтеры с другими правилами
в отдельные пакеты. Семантические пустые строки из командного скилла сохраняются.

## 2. Имена и организация

- Файлы и каталоги: kebab-case. Типы и классы: PascalCase.
- Переменные и функции: camelCase; имя объясняет содержимое или действие.
- Булевы значения обычно начинаются с is. Для преобразования — Boolean(value), без !!.
- Модульные значения: camelCase, например worldSettings и itemDefinitions.
  Единственный регистр для новых модулей; внешние API сохраняют свои имена.
- UI callbacks: onClick, onInventoryChange. Не менять обязательные методы Phaser/Colyseus.
- Код, сетевые ключи и комментарии API — на английском; UI и проектные документы — на русском.
- Функция выполняет одно понятное действие; отдельная функция явно координирует шаги.
- Для функций с одним возвращаемым выражением — стрелка с неявным возвратом,
  если это сохраняет this и контракт. Вложенные тернарные операторы запрещены.
- Сложные смысловые проверки именуются; guard clauses сохраняют short-circuit семантику.
- Повторяющуюся нормализацию одного источника выполнять один раз в нужной области.
- Не вводить абстракцию ради единственного использования; не собирать несвязанный код
  в общий utils. Разделять модули по ответственности, а не ради фиксированного числа строк.

## 3. Типы

- TypeScript strict, noUncheckedIndexedAccess и exactOptionalPropertyTypes обязательны.
- Использовать readonly для контента, команд и границ API; mutable мир имеет явного владельца.
- Входящие неизвестные значения — unknown с проверкой, не any или необоснованный cast.
- Импорты типов помечаются import type / inline type.
- Экспортируемые функции имеют явные типы входов и результата.
- Состояния и команды — discriminated unions; ветки обрабатываются исчерпывающе.
- Предпочитать строковые literal unions и as const данным вместо runtime enum.
  erasableSyntaxOnly запрещает TypeScript-конструкции с дополнительной runtime-семантикой.
- Нет non-null assertion для маскировки неполной инициализации.
- Не подставлять fallback через ||, если 0, false или пустая строка допустимы.
- Имена игровых величин отражают единицы: deltaSeconds, expiresAtMs, weightGrams.

## 4. Импорты и зависимости

simple-import-sort задаёт общий воспроизводимый порядок импортов и экспортов.
Внутри пакета — относительные импорты, между пакетами — публичный workspace API.
Не сортировать вручную значимые side-effect imports; если порядок принципиален,
потребуется локальное исключение с объяснением. Не использовать собственный barrel
внутри пакета. Циклы и запрещённые зависимости проверяются dependency-cruiser.

Добавление библиотеки: понятная польза, совместимость, лицензия и стоимость поддержки.
Точные версии и один lockfile. Не добавлять одновременно разные библиотеки для одной задачи.

## 5. Правила игровых систем

- Нет Date.now(), Math.random(), DOM, Node API и самостоятельных таймеров в общем ядре.
  Время и RNG передаются явно. Абсолютное время предоставляет серверный адаптер.
- Симуляция использует фиксированный шаг; логика не зависит от FPS или скорости UI.
- Настройки оружия, зомби, выживания и лута находятся в content, а не в Scene.
- Scene/Room — адаптеры; правила урона и инвентаря находятся в simulation.
- Нет async IO внутри шага мира; нет параллельной записи общего mutable состояния.
- Ошибки и отмена async-операций обрабатываются явно. Непроверенные Promise запрещены;
  void не используется как способ скрыть отсутствующую обработку ошибки.
- Ресурсы освобождаются на завершение жизненного цикла.
- Production-код не импортирует тестовые fixtures. Нужные заглушки остаются в тестах.
- Production-код приложений использует адаптер логирования вместо console.log.
  Отладочные данные и секреты не попадают в сетевые сообщения.

## 6. Проверки и исключения

Локальный полный запуск: npm run check. Автоформатирование: npm run format.
CI запускает ту же команду после npm ci.
Строгая типизация и ограничения ядра проверяются ESLint; граф — dependency-cruiser.
Поведение этих ограничений проверено отдельными тестами с разрешёнными и
запрещёнными примерами. Архитектуру, владение состоянием и жизненный цикл
нельзя целиком доказать линтером: они также проверяются тестами и ревью.

Typecheck проверяет tools/architecture-policy.ts и все созданные workspace-пакеты.
В T001 добавлены build клиента/сервера и Playwright smoke-проверки.
Клиентский tsconfig использует DOM и разрешение Bundler; серверный — NodeNext.
При появлении ядра его tsconfig использует ES2022 без DOM и Node types.
Все наследуют tsconfig.base.json; каждый новый workspace включает typecheck/build.

Изменение общих правил — самостоятельный PR с причиной и проверкой.
eslint-disable допускается точечно, с конкретным обоснованием.
Не отключать правило глобально ради одного неудобного файла.
Не считать skipped-проверку пройденной. Тесты проверяют реальные сценарии,
без реальных задержек и зависимостей от случайного времени выполнения.

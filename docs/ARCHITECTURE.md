# Архитектура ZombiSurvive

Статус: принятая основа проекта. Изменения границ оформляются отдельным
архитектурным решением и PR. Этот файл определяет техническую архитектуру;
[GAME_DESIGN.md](../GAME_DESIGN.md) определяет игровые требования.
[CODE_STYLE.md](CODE_STYLE.md) определяет правила кода.

## 1. Выбранный подход

Модульный монорепозиторий на TypeScript. Один сервер симуляции владеет одним миром.
Браузерный клиент отображает разрешённое ему состояние и отправляет намерения игрока.
Сервер запускается на компьютере игрока-хоста. Одиночная игра и кооператив
с друзьями используют одну серверную симуляцию; отдельный платный хост не требуется.
Решение: [ADR 0001 — локальный хост и кооператив](adr/0001-local-host-coop.md).

Игровая логика отделена от Phaser, транспорта, БД и интерфейса.
Цель — небольшая группа друзей. Максимальная вместимость определяется по
измерениям на компьютере хоста; публичный мир на 100 игроков вне текущего scope.
Микросервисы, распределённый мир и отдельный ECS-фреймворк пока не вводятся.

## 2. Технологии

- Node.js 24; конкретная версия — .nvmrc. Пакетный менеджер — npm, один package-lock.json.
- Версия игры — SemVer в корневом package.json и package-lock.json. Клиент показывает
  её в заголовке из production-сборки Vite. После каждой завершённой задачи разработки
  повышать patch; если меняется публичный контракт или масштаб функции требует
  нового minor/major, выбирать соответствующий уровень SemVer. Версии приватных
  workspace-пакетов относятся к npm-сборке и не являются версиями игры.
- TypeScript, ESLint flat config, typescript-eslint, Prettier и dependency-cruiser.
  Совместимые точные версии — package.json и lockfile.
- Клиент: Phaser 4.2.1 + Vite 8.3.4, зафиксированы в T001.
- Сервер: Node.js; HTTP health endpoint и Colyseus/WebSocket в T003:
  @colyseus/core 0.18.18, @colyseus/ws-transport 0.18.4, клиент @colyseus/sdk 0.18.5 (MIT).
  В одиночном режиме доступ только
  через loopback; кооператив явно разрешает доступ через выбранный сетевой интерфейс.
  Браузерный клиент и игровой endpoint обслуживает один локальный сервер.
  Для loopback используется HTTP/WS; защищённое подключение друзей описано в ADR 0001.
  С T005A `npm start` запускает собранный сервер и раздаёт клиент с того же origin;
  dev и preview используют Vite proxy. T003 создаёт один Room при старте процесса, запрещает
  клиенту создавать комнаты и сохраняет пустую комнату до остановки сервера.
  Все solo-вкладки получают одного персонажа, серверные worldId/playerId
  устойчивы до завершения процесса. T005B добавляет отдельные идентичности
  участников кооператива; cookie одного профиля браузера связывает его вкладки.
- Хранение первой версии: SQLite на компьютере хоста, очередь коротких транзакций.
  Хост владеет файлами общего мира, персонажами участников и локальными бэкапами.
- UI: HTML/CSS поверх игрового canvas. React/FSD пока не используются.
- Проверки запуска: Playwright 1.64.0, production-сборки клиента и сервера.
  Vitest 5.0.4 (MIT) проверяет игровую логику с T004; Vite 8.3.4 также
  закреплён в корне как его совместимый peer. Unit-тесты типизируются и проходят
  общий lint; vitest.config.mjs отделяет их от Node/Playwright-наборов.
  Проверки инфраструктурных ограничений используют Node test runner.

Не обновлять отдельный инструмент до latest без проверки диапазонов совместимости.
В текущем наборе TypeScript 6.0.3 совместим с typescript-eslint 8.71.2;
TypeScript 7 пока вне заявленного диапазона этого линтера.

## 3. Модули и единственное направление зависимостей

```text
apps/client       отрисовка, ввод, сетевой адаптер, UI и аудио
apps/server       игровой цикл, сетевой адаптер, доступ, БД и эксплуатация
packages/domain   общие игровые типы, ID, значения; без сетевых сообщений
packages/content  определения предметов, зомби, балансовые параметры
packages/protocol сетевые DTO, команды, события и версия протокола
packages/simulation движение, бой, AI, инвентарь, выживание
packages/worldgen генерация местности и локаций по seed
tools             проверки и служебные инструменты разработки
tests             интеграционные проверки и проверки инструментов
assets            источники ассетов и лицензии
docs              требования, правила и архитектурные решения
```

| Модуль     | Разрешённые зависимости на пакеты проекта       |
| ---------- | ----------------------------------------------- |
| domain     | Нет                                             |
| content    | domain                                          |
| protocol   | domain                                          |
| simulation | domain, content                                 |
| worldgen   | domain, content                                 |
| client     | domain, content, protocol, simulation, worldgen |
| server     | domain, content, protocol, simulation, worldgen |

Матрица для автоматической проверки: tools/architecture-policy.ts.
Все изменения матрицы одновременно отражаются в этом документе.

- Клиент и сервер не импортируют код друг друга.
- Общие пакеты не импортируют приложения, Node runtime, Phaser, Colyseus или БД.
- Runtime-зависимости общего ядра добавляются только через явное решение.
- Внешние пакеты доступны адаптерам приложений и тестам по назначению.
- Импорт другого пакета только через @zombi-survive/<name> и его src/index.ts.
  Межпакетные относительные импорты внутренних файлов также запрещены проверкой.
- Внутри пакета прямые относительные импорты разрешены; собственный index.ts
  не используют для импорта внутренних функций, чтобы не создавать циклы.
- src/index.ts экспортирует публичный API явно. Общего barrel на все пакеты нет.
- При создании пакета задать exports; конфигурацию разрешения workspace-импортов
  согласовать с TypeScript, Vite, Node и dependency-cruiser.

В T002 созданы domain и protocol; контракты — [MOVEMENT_PROTOCOL.md](MOVEMENT_PROTOCOL.md).
Публичные exports используют исходники при условии development, собранные JS
по умолчанию и декларации для TypeScript. Node dev включает это условие явно,
Vite использует его в development. Проверка графа также читает исходники.
С T004 созданы content и simulation; T011 добавляет worldgen. Корневые build/lint/typecheck сначала
собирают общие пакеты через build:core: domain → protocol → content → simulation → worldgen.
Команда build:contracts сохраняется для отдельной сборки domain/protocol.

domain нужен, чтобы protocol и simulation использовали общие значения без
зависимости игровой логики от транспорта. Сетевые DTO и модель сохранения
не заменяют внутреннюю модель мира.

## 4. Симуляция и владение состоянием

- Шаг движения T004 фиксирован и независим от FPS: 20 Гц, 0.05 секунды,
  обычная скорость 4 м/с. T009 добавляет спринт 7 м/с, нормализованную
  выносливость 0–1, расход 0.2/с и восстановление 0.1/с; истощение запрещает
  спринт до 20%. T010 добавляет Ctrl-скрытность 2 м/с с приоритетом над Shift,
  восстановлением запаса и радиусом шума 2/8/16 м для скрытности/ходьбы/спринта;
  покой и полная блокировка стеной обнуляют шум. Протокол v5 передаёт намерение
  скрытности, режим и вычисленный сервером шум всех персонажей.
  Сервер и клиентское предсказание используют один шаг. Параметры прототипа заданы в content; баланс уточняется
  после игровой проверки. stepPlayerMovement принимает явный stepSeconds,
  отклоняет несовпадение с movementStepSeconds, нормализует диагональный ввод
  и возвращает новое PlayerMovementState без мутации входов.
  В T005 Room вызывает этот шаг через управляемый Colyseus setTimestep
  с интервалом 50 мс. Каждый callback завершает ровно один фиксированный шаг;
  measured delta не меняет скорость шага. При перегрузке симуляция замедляется,
  накопленная задержка не догоняется неограниченной серией шагов.
  Локальный адаптер хранит один pending-ввод на подключение, применяет последние
  намерения на шаге и формирует отдельный ack для каждого подключения.
  Удерживаемое направление действует максимум десять шагов без свежего ввода.
  Клиент отправляет WASD до 10 Гц; T008 предсказывает своё движение
  общими правилами, согласуя его с сервером (см. MOVEMENT_PROTOCOL.md).
- Время шага передаётся явно: stepSeconds и tick. Время жизни тела — отдельная
  абсолютная отметка сервера, поскольку 24 часа означают реальные часы.
- RNG передаётся явно; генерация использует seed и версию генератора.
- Общая функция движения используется сервером и клиентским предсказанием.
  Одинакового seed недостаточно для гарантии воспроизводимости всей симуляции:
  нужны одинаковые шаг, порядок обработки, правила и состояние RNG.
- Для предсказания выбираем воспроизводимый порядок обновления сущностей.
  Точность чисел и допустимые отклонения проверяем на целевых средах.
- Идентификаторы устойчивы; игровые величины имеют явные единицы: секунды,
  координаты мира, масса. Рендер переводит координаты мира в пиксели.
- Mutable-состояние мира изменяется назначенными системами на шаге сервера.
  Контент и команды — readonly. Нет глобального изменяемого singleton мира.
- UI и сеть не меняют здоровье, владельца предмета или результат попадания напрямую.
- Столкновения — общая игровая логика. Phaser physics не является серверным
  источником правил движения и столкновений.
- Синхронный шаг не выполняет await, запросы БД, чтение файлов или сетевые вызовы.
  Адаптеры подают завершённые результаты через очередь команд следующего шага.
- Последовательность систем зафиксировать до первой реализации боя;
  события не должны случайно обрабатываться дважды из-за порядка callback.

Объекты и функции предпочитаем для правил и данных; классы используем для
жизненного цикла Scene, Room и адаптеров, где этого требует библиотека.
Наследование не является механизмом описания всех предметов или типов зомби.

## 5. Асинхронность и сеть

- Одиночный режим принимает только локального игрока на loopback. Кооператив
  включается явно; друзья подключаются в браузере к адресу компьютера хоста
  по LAN или через интернет в защищённой частной виртуальной сети.
- Сервер раздаёт собранный клиент; игровой URL определяется от origin страницы.
  Dev-сборка может использовать локальный proxy. Адрес 127.0.0.1 не зашивается
  в клиентский игровой endpoint, поскольку у друга он указывает на его компьютер.
- T005A загружает в память только index.html и JS/CSS из assets готовой сборки
  при старте; пути определяются относительно серверного модуля, независимо от cwd.
  HTTP не читает произвольные пути с диска, не выдаёт source maps и не подставляет
  HTML для отсутствующих ресурсов. GET/HEAD имеют MIME types и no-store;
  изменения сборки требуют перезапуска процесса. При отсутствии сборки запуск
  завершается до открытия порта с подсказкой выполнить npm run build.
  Статические ответы завершаются через Node HTTP end(body) перед маршрутизатором
  Colyseus с общей проверкой Host/Origin: его Response-адаптер оставлял большие
  ответы открытыми после backpressure. Игровые маршруты остаются у Colyseus.
  Production по умолчанию разрешает только origin сервера. Dev явно запускается
  с --dev, не требует dist и разрешает origin Vite. CLIENT_ORIGIN добавляет
  только проверенный HTTP origin выбранного хоста; Host и WebSocket Origin проверяются
  в обоих режимах. Доступ solo остаётся привязан к 127.0.0.1.
- T005B включает кооператив только при явном COOP_HOST: private IPv4 локального
  интерфейса, без wildcard/public/loopback адресов. Listener привязан только к нему,
  Host/Origin разрешают выбранный адрес, клиент использует origin страницы.
  Dev с COOP_HOST запрещён; собранный клиент и HTTP/WS работают в доверенной LAN.
  T005C добавляет COOP_NETWORK=tailscale: COOP_HOST обязателен и допускает только
  IPv4 диапазона 100.64.0.0/10, назначенный локальному интерфейсу. Без этого режима
  диапазон отклоняется; lan остаётся значением по умолчанию. Неверный режим
  останавливает запуск. Проверка адреса не удостоверяет VPN: оператор должен
  выбрать адрес Tailscale и настроить защищённый маршрут. Listener, Host/Origin,
  приглашения и same-origin HTTP/WS используют прежний путь без proxy.
  Инструкция и отдельная интернет-приёмка: [INTERNET_COOP.md](INTERNET_COOP.md).
  Firewall/роутер и настройки VPN приложение не меняет.
- WorldAccess создаёт 8 одноразовых приглашений на 30 минут. Они сохраняются
  в файле 0600 внутри временного каталога 0700 и удаляются при штатном shutdown.
  В журнал выводится только путь к файлу. POST /session с доверенным Origin
  атомарно погашает приглашение и выдаёт случайную HttpOnly SameSite=Strict cookie,
  имя которой включает PORT. В таблицах lookup хранятся SHA-256 digest секретов.
  Cookie проверяется до matchmaking, до WebSocket upgrade и в Room onAuth;
  onJoin получает только серверный playerId. ID из payload не даёт полномочий.
  Текущий cookie сохраняет идентичность, не погашая другое приглашение.
- До 8 персонажей и 16 соединений ограничивают ресурсы прототипа; это не результат
  нагрузочного измерения. Mutable-состояние и управление разделены по playerId,
  порядок pending-команд общий, ack относится к подключению. Вкладки одного
  участника делят управление по правилам T005; ввод другого участника не влияет
  на него. Snapshot v2 содержит своего игрока и позиции остальных, без сессий
  и приглашений. Клиент отображает подтверждённые позиции и удаляет fragment
  приглашения из истории до HTTP-входа. После disconnect персонаж останавливается
  и остаётся в мире; cookie возвращает его на ту же позицию до остановки хоста.
  В кооперативе сессии, приглашения и позиции пока находятся только в памяти.
  T013 сохраняет идентичность мира и персонажа и позицию только в solo.
- Все участники одного процесса используют один мир; каждому назначается свой
  персонаж. Повторный вход восстанавливает участника, а не создаёт новый мир.
- Доступ друзей требует приглашения и привязки к серверной идентичности.
  Локальное размещение не отменяет проверки команд, Origin и прав на персонажа.
- Остановка, сон или недоступность хоста завершают связь со всеми клиентами;
  UI сообщает о потере хоста, мир не переносится автоматически на другой компьютер.

- Сервер проверяет форму, диапазоны, полномочия, частоту и допустимость команд.
  TypeScript не заменяет runtime-проверку сетевого JSON.
- Команда действия имеет ID; повтор после переподключения не дублирует действие.
- Изменения мира сериализованы. Сетевые callback ставят команды в очередь,
  а не обходят правила симуляции.
- Результаты загрузки чанков имеют ключ мира, координаты и версию запроса;
  устаревший результат не заменяет новый мир или состояние после переподключения.
- Ресурсы Scene/Room освобождаются: подписки, таймеры, input handlers, звук.
  Отмена и dispose — явная часть жизненного цикла.
- Потеря соединения не создаёт новый персонаж и не обходит уязвимость в бою.
- Синхронизируется область интереса, приватные данные других игроков не отправляются.
- Предсказание применяется к движению; лут, урон и выдача предметов подтверждаются сервером.

## 6. Мир и сохранение

T006 добавляет локальную камеру и прицел, перевод координат canvas в мировые
координаты и движение по клику. Клиент отправляет намерение movement-target;
протокол v3 использует общий sequence с клавиатурой. Сервер выбирает последнее
намерение и вызывает чистый stepPlayerToward из simulation с фиксированным шагом:
скорость прежняя, последний шаг ограничен расстоянием до цели. Тайм-аут ввода,
контроль соединения и остановка чужой вкладки работают по прежним правилам.
Клиентский прицел пока не отправляется серверу. Сетка рисуется только в видимой
области, без загрузки большого мира. Поиск пути отложен.

T007 хранит три статических прямоугольных препятствия в content. Клиент рисует
эту же геометрию; сервер после stepPlayerMovement/stepPlayerToward вызывает чистую
resolveMovement из simulation. Квадрат персонажа 0.7 × 0.7 м расширяет границы
препятствий; непрерывная проверка отрезка находит первый контакт и позволяет
скольжение вдоль грани. До двух контактов ограничивают обе оси без зависимости
от порядка препятствий. Начальная позиция должна быть свободна; восемь spawn
проверены тестом. Динамические препятствия и исправление проникновения не входят
в этот прототип. Столкновений между персонажами нет.

Протокол v3 не меняется: препятствия фиксированы в одной сборке клиента/сервера,
snapshot передаёт уже ограниченную сервером позицию. Клиент не использует Phaser
physics. T011 задаёт контракт процедурной геометрии ниже; T012 добавляет локальную загрузку соседей.
Цель за стеной сохраняется до новой команды или отмены ввода; обход ручной.

T008 добавляет клиентский адаптер MovementPrediction с явным локальным временем.
Он переигрывает ограниченную историю намерений от каждого snapshot, удаляет
обработанные sequence по ack и использует общую simulation со столкновениями.
Экстраполяция ограничена 500 мс; переполнение 64 записей оставляет серверную
отрисовку до нового подключения. Свой персонаж/камера используют предсказание,
остальные персонажи и UI координат — подтверждённые значения. Протокол v3
и серверные правила не меняются. Оценка задержки приближённая, коррекции прямые;
точная синхронизация часов и интерполяция других игроков отложены.

T011 добавляет чистый пакет worldgen и readonly WorldChunk/WorldChunkKey в domain.
Ключ: seed (1–128 UTF-16 code units), generatorVersion (сейчас 1), целые chunkX/chunkY
в пределах ±1 000 000. Центр чанка находится в (chunkX × 64, chunkY × 64) м;
полуоткрытые границы — центр ±32 м. Местность состоит из 1024 плиток 2 × 2 м
(grass/dirt/gravel), непроходимая геометрия — WorldObstacle в мировых координатах.
Хеш FNV-1a с отдельными каналами местности/камней зависит от всего ключа;
генерация не использует runtime API, глобальное состояние и порядок соседних запросов.
Результат глубоко заморожен. Геометрия v1 защищена контрактной SHA-256 фикстурой.

Три прежних препятствия стали шаблоном стартовых руин в content. Генератор переносит
его в центр участка и добавляет камни в угловых областях, сохраняя восемь spawn.
Край шириной 2 м всегда травяной и свободен от препятствий: стыки одинаковы
по всем четырём сторонам, включая отрицательные координаты. Это начальное правило
v1; дорог и региональной генерации пока нет. Terrain декоративный и проходимый;
столкновения используют только obstacles. ID включает версию и координаты чанка,
уникален внутри одного мира. Seed относится к ключу мира, а не к ID препятствия.

initialWorldChunk сохраняет публичный эталон начала мира: seed zombi-survive,
версия 1, координаты (0, 0). T012 добавляет чистую loadWorldChunks: на входе
позиции и предыдущее readonly-окно, на выходе объединение соседей 3 × 3.
Координата чанка — floor((метры + 32) / 64), включая отрицательные значения.
Неизменившееся окно сохраняет ссылку; общие чанки переиспользуются, дальние
не входят в результат. Ключи другого seed/версии не переиспользуются.
Глобального изменяемого кеша нет: владельцы — адаптеры приложений.

WorldTerrain клиента держит девять чанков вокруг отображаемого персонажа,
по одному Phaser Graphics на чанк. Graphics вне viewport скрыты, чтобы их
command buffer не исполнялся каждый кадр; на стыке видимы оба участка.
Дальние Graphics уничтожаются; disconnect
и shutdown освобождают окно. MovementPrediction отдельно держит до девяти
чанков вокруг авторитетной позиции: ореол 64 м покрывает движение и footprint
за максимум 500 мс экстраполяции. Reset удаляет ссылки. Сервер перед движением
обновляет объединение окон всех существующих персонажей: максимум 72 чанка для
восьми, пересечения не дублируются. Отключённые персонажи пока остаются в мире,
поэтому их окна сохраняются до остановки процесса. При переходе в соседнее
окно создаются только недостающие чанки; возврат воспроизводит прежнюю геометрию.

Генерация синхронная и ограниченная размером окна, без IO, await, таймеров и
поздних результатов. Впервые чанк создаётся при необходимости в адаптере шага/
отрисовки; геометрия доступна до resolveMovement. Настройка seed, worker-потоки
и передача ключей/геометрии по сети отложены. Протокол движения v5 не меняется;
клиент и сервер нужно пересобирать вместе. Генератор v1 и его фикстура неизменны.

Чанки воспроизводятся по seed, координатам и версии генератора. Крупные дороги
и поселения согласованы на уровне региона. Сохраняются изменения базового мира.
Изменение генератора не меняет уже исследованную карту без миграции.

При работающем сервере хоста время, погода и таймеры лута продолжаются без игроков.
При закрытии последней вкладки вне боя Room записывает точную позицию до удаления
персонажа из активного мира. Повторный вход создаёт управляемого персонажа на этой
позиции, с сохранёнными HP и вещами. В работающем хосте состояние выносливости
остаётся в памяти, а движение останавливается. Закрытие одной из нескольких вкладок не
удаляет персонажа. При активном бое или кровотечении выход пока оставляет его
в мире; симуляция угроз после выхода добавляется в T044.
Движение зомби рассчитывается в активных областях; область с отключённым уязвимым персонажем остаётся активной.
Остановка или сон компьютера хоста останавливает симуляцию мира. После запуска
восстанавливаются сохранённые состояния; движение, AI, погода и лут за перерыв
не симулируются. Абсолютные сроки в реальных часах проверяются при восстановлении.
Закрытие браузера хоста не останавливает отдельный серверный процесс. Уязвимость
отключившегося персонажа действует, пока мир работает; остановка всей сессии
не должна запускать новую симуляцию в браузере оставшегося участника.

Хранилище имеет самостоятельную версию схемы и миграции. Доменная модель,
сетевой DTO и запись БД разделены явными преобразованиями.
Перенос предмета и смерть — атомарные изменения. У предмета один владелец.
Критические изменения подтверждаются после устойчивой записи; перед реализацией
определить модель восстановления снимков и подтверждённых изменений.
Движение можно сохранять периодически с явно заданным допустимым окном отката.

T013 реализует первый solo-срез хранилища в apps/server/src/solo-world-store.ts
([ADR 0002](adr/0002-solo-position-persistence.md)).
Встроенный node:sqlite (DatabaseSync) создал в T013 схему user_version=1 и одну запись:
worldId/playerId, seed/generatorVersion, xMeters/yMeters. DTO сохранения отделён
от MovementSnapshot и PlayerMovementState; stamina/намерения/sequence не хранятся.
При загрузке проверяются схема, генератор, ID, конечные координаты, диапазон чанков
и отсутствие пересечения footprint с препятствиями. Несовместимый/повреждённый файл
не заменяется новым. Клиентский протокол v5 и генератор v1 не меняются.

main открывает сохранение до запуска listener и передаёт восстановленные ID/позицию
в Room. По умолчанию путь .local/solo.sqlite вычисляется от расположения модуля,
а не cwd; WORLD_SAVE_PATH принимает только абсолютный путь. Кооператив не открывает
solo-хранилище. Файлы исключены из Git и недоступны через статическую HTTP-раздачу.
Файл имеет права 0600, создаваемый каталог — 0700.

Room вызывает короткий синхронный UPDATE отдельным таймером раз в секунду,
после завершённых шагов, без очереди ожидающих записей и IO внутри step().
SQLite DELETE journal и synchronous=FULL обеспечивают атомарную запись;
locking_mode=EXCLUSIVE удерживает единственного владельца между транзакциями.
При штатной остановке Room прекращает шаги и таймер, записывает позицию,
затем отключает клиентов; Server закрывает БД. Ошибка записи останавливает
хост с exitCode=1, не скрывается внутри Colyseus shutdown. При SIGKILL
восстанавливается последний commit: обычное окно отката до секунды, при блокировке
event loop — больше. Синхронный fsync может задержать Node event loop; workers,
измерение задержек и автоматические бэкапы отложены. T022 добавляет первую миграцию.

Тело и оставшиеся вещи истекают через 24 реальных часа даже после остановки
сервера. Уже забранные вещи не удаляются. Бэкап проверяется восстановлением.

## 7. Производительность и проверки

- Профилируем время шага, память, трафик и очередь сохранения на компьютере хоста.
- Проверяем одного игрока и двух участников на разных устройствах, завершение
  хоста, повторное подключение и восстановление локального мира.
- Пространственный индекс используется для соседей, столкновений и видимости.
- AI и генерация имеют ограничение работы за шаг; дальние чанки освобождаются.
- Pooling, workers и сложные структуры вводим после измерения реальной проблемы.
- Проверяем правила отдельно от графики, а взаимодействие — интеграционными сценариями.
- Тесты используют контролируемые шаги времени и RNG; реальный sleep не задаёт исход теста.
- Проверяем повторные команды, смерть один раз, конкурирующий подбор, восстановление
  и гонки загрузки чанков. Перед увеличением вместимости проводим нагрузочные проверки.

Для новой зависимости пакетов, нового архитектурного слоя, движка или хранилища

## T015 — один предмет и простой контейнер

Domain задаёт Item/GroundItem и взаимоисключающие ItemLocation: земля либо
контейнер с playerId. Content задаёт один бинт starter-bandage в (2, 2) м и
радиус 1,5 м. Чистая pickUpItem в simulation проверяет ID, дистанцию и свободный
проход через статическую геометрию. Возвращается одно новое расположение вещи;
повторный запрос не меняет владельца и не создаёт копию.

LocalWorldPickup владеет расположением и хранит максимум одну ожидающую команду
на сессию. Room после шага движения синхронно применяет подбор по проверенной
серверной позиции/идентичности. Для предмета у старта используется геометрия
initialWorldChunk: вся область подбора находится внутри этого чанка. Нет IO/await
между удалением предмета с земли и присвоением контейнеру. Disconnect удаляет
ожидающий запрос; переподключение с тем же playerId сохраняет контейнер в памяти.

Протокол v5 дополнен pickup-item (тип, версия, itemId), pickup-state-request и
pickup-state (версия, worldId/playerId, tick, groundItem, items). Количество
предметов ограничено одним; unknown проверяется на обеих границах. Сервер не
принимает от клиента координаты/владельца. Snapshot содержит только контейнер
получателя. Клиент игнорирует старые ticks и прежние подключения, проверяет
идентичность мира/игрока. При disconnect UI и маркер очищаются. Предсказание
движения не выдаёт вещи; кнопка доступна по подтверждённой дистанции.

Состояние вещей живёт только в процессе хоста; после его рестарта бинт снова
на земле и контейнер пуст. SQLite v1 сохраняет только прежнюю позицию/идентичность;
сохранение предметов и миграции — будущая задача. Нет сетки, массы, экипировки,
использования бинта или респавна лута. Кооперативная приёмка остаётся отложенной.

## T016 — размещение в сетке

Domain задаёт InventoryCell и InventoryItem; ItemLocation контейнера содержит
подтверждённую верхнюю левую ячейку. Content задаёт сетку 4 × 3, лимит 2000 г
и бинт 2 × 1 / 100 г. Правила simulation проверяют весь прямоугольник, границы,
пересечения и массу; при переносе вещь учитывается один раз. Подбор использует
первое свободное место в порядке строк. Правила готовы для нескольких вещей,
но серверный прототип по-прежнему содержит только один бинт T015.

К протоколу v5 добавлены inventory-move (itemId, cell) и inventoryVersion=1
в команде/снимке pickup-state; items снимка теперь содержат cell. Версия отдельно
фиксирует формат сетки; старый формат клиент отклоняет. Protocol проверяет форму,
целые ограниченные индексы, ID и версии, simulation — реальные размеры/массу.
Клиент дополнительно проверяет применимость снимка к своим content-правилам.
Сервер игнорирует поддельные поля размеров/массы/владельца. Pending-очередь хранит
последнее действие на сессию, не более одного; следующий фиксированный шаг
проверяет реального владельца и применяет переход без IO. Абсолютная ячейка и
стабильный itemId делают повтор переноса идемпотентным. Disconnect удаляет pending.

UI показывает подтверждённые клетки и массу, выбирает предмет кнопкой и посылает
ячейку по клику/Enter; недопустимое размещение объясняется локально. UI не двигает
предмет до snapshot сервера, отключение очищает сетку и выбор. Обычный поток
snapshots не пересоздаёт кнопки и не сбрасывает выбор при неизменном содержимом.
Reload/retry сохраняют размещение только в течение жизни процесса хоста.
Поворот, drag-and-drop, новые вещи, экипировка, применение и запись на диск
отложены. Генератор v1 и SQLite v1 не меняются, кооператив не возобновляется.

## 10. Медленный зомби (T017)

`ZombieState` в domain содержит ID, позицию и ID текущей цели либо null.
Content задаёт стартовый спавн (-8, 0), сетку спавнов в каждом чанке (T019), скорость 1.5 м/с,
зрение 12 м, удержание цели до 18 м, остановку в 0.9 м и запас окна пути 4 м.
Чистый `stepZombie` в simulation получает игроков, геометрию и фиксированный
шаг 0.05 с. Обнаружение требует прямой видимости, при равной дистанции порядок
задаёт ID игрока. Захваченная цель удерживается за препятствиями до выхода
из радиуса/отключения. Для перемещения используется visibility graph углов
препятствий, расширенных на общий footprint 0.35 м с запасом 0.01 м.
Поиск ограничен прямоугольником start/target плюс 4 м; финальный шаг всегда
проверяет общий `resolveMovement`. Нет пути — нет движения.

Room выполняет движение игроков → подбор/перенос → AI → отправку snapshots.
`LocalWorldZombie` получает только подключённые сессии, устраняет дубли игрока
из нескольких вкладок и загружает объединённые окна геометрии вокруг игроков.
При отсутствии игроков он освобождает cache геометрии и сбрасывает цели.
AI активен только в 18 м от игроков. В snapshot попадают зомби в 22 м, до 256 записей.
Движение и рендер игроков не зависят от AI; динамические столкновения с игроками,
слух и сохранение зомби на диск остаются следующими задачами.

Аддитивное сообщение `zombie-state` использует protocolVersion=5 и отдельную
zombieVersion=1: worldId, tick, zombies (0–256 записей с уникальными ID). Команд управления зомби
нет. Клиент проверяет unknown, версии, ID, конечные координаты и tick;
отклоняет чужой мир, игнорирует старые тики и устаревшие комнаты.
Phaser отображает подтверждённую позицию без предсказания AI; disconnect
уничтожает маркеры, а retry/reload получает текущее состояние процесса хоста.
Генератор v1 и SQLite v1 не меняются; кооперативная приёмка остаётся PAUSED.

## 11. Атака зомби и здоровье (T018)

`PlayerHealth` и `ZombieAttackState` находятся в domain; баланс в content:
100 HP, урон 10, радиус 1.1 м и интервал 20 фиксированных шагов. Чистый
`stepZombieAttack` проверяет совпадение цели/владельца HP, положительные HP,
дистанцию и прямую видимость по общей статической геометрии. Первый удар
требует полного интервала, как и повторные. Потеря досягаемости, отключение
или смена цели сбрасывают замах; HP никогда не становятся отрицательными.

Порядок Room: движение → подбор/перенос → AI → ближний бой → атаки живых зомби → snapshots. AI возвращает
своё подтверждённое состояние и уже загруженную геометрию. LocalWorldCombat
хранит HP по серверным playerId и независимые таймеры атак по zombieId;
вызов один на шаг, независимо от числа сессий. Атаковать можно только
подключённую цель; HP отключённых остаются в памяти. Сетевых команд урона,
здоровья и лечения нет. Шаг не содержит IO или await.

Аддитивный `health-state` с protocolVersion=5/healthVersion=1 содержит
worldId/playerId, tick, health и maxHealth только получателя. Клиент проверяет
unknown, идентичность и монотонность тика, игнорирует прежние комнаты и
сообщения до готовности, очищает HUD при disconnect. Движение не предсказывает
HP. При 0 HP атаки прекращаются; смерть/тела/респавн и ограничения действий
будут отдельными задачами. HP живут до остановки процесса, SQLite v1 и
генератор v1 не меняются. Кооперативная приёмка остаётся PAUSED.

## 12. Ближний бой и популяция (T019/T020)

LocalWorldZombie один раз заселяет каждый загруженный чанк девятью зомби:
сетка смещений -24/0/24 м, центральный спавн (-8, 0) относительно центра чанка.
Позиции безопасны для геометрии генератора v1 и общего footprint; это проверяет тест.
ID зависят от чанка и ячейки; стартовый ID сохраняется. Посещённые чанки и
позиции живут в памяти процесса; возврат в том же процессе не воскрешает убитых.
HP и гибель сохраняются с T046.
Геометрия ограничена окнами подключённых игроков; история популяции растёт
с числом посещённых чанков. Сохранение позиций и длительный нагрузочный тест отложены.

LocalWorldMelee принимает только намерения экипировки стартового оружия и взмаха.
Domain задаёт MeleeWeaponId и runtime-проверку четырёх ID; content/meleeWeapons
содержит неизменяемые определения дубинки, ножа, лома и топора (баланс в README).
Protocol meleeVersion=2 требует weapon у equip-weapon; v1 отклоняется.
Авторизация связывает сессию с персонажем через MovementSnapshot. На шаге сервер
проверяет положительные HP, экипировку и cooldown выбранного оружия по playerId;
последняя команда сессии заменяет предыдущую, отключение удаляет очередь.
Промах также расходует cooldown. Чистый findMeleeTarget выбирает одного ближайшего
достижимого зомби в радиусе оружия, при равенстве — по ID. LocalWorldZombie
применяет переданный сервером урон к 100 HP, удаляет убитого до расчёта атак
зомби того же шага. Новый выбор оружия не сбрасывает паузу предыдущего удара.
Каждый персонаж получает четыре стартовых оружия отдельно от сетки T016.
Экипировка, cooldown и HP не сбрасываются при reconnect, живут до остановки хоста.
Клиент получает отдельный melee-state, очищает UI при disconnect и блокирует F
при повторе клавиши, вводе текста, отключении и нулевых HP.

## 13. Имя solo-профиля (T022)

Domain задаёт валидатор отображаемого имени: 1–24 символа, кириллица/латиница,
цифры, обычный пробел, дефис и подчёркивание, без крайних пробелов. Имя — подпись;
playerId и авторизация не меняются. SQLite v2 добавляет display_name и name_revision
в единственную solo_world. Миграция v1 выполняется внутри начальной EXCLUSIVE
транзакции; до успешной проверки старые ID, генератор и позиция не подтверждаются.

Обработчик запроса rename-player использует профиль авторизованной сессии и
выполняет commit вне timestep. Только после успешной записи меняется кэш профиля
и возвращается saved. Ошибка возвращает unavailable без нового имени. Повтор
того же имени не увеличивает ревизию. Общая очередь Node упорядочивает записи
вкладок; последнее принятое имя побеждает. Room читает кэш без IO для profile-state.
Аддитивные DTO profileVersion=1 используют protocolVersion=5 и worldId/playerId;
старые/чужие комнаты и более ранние ревизии не откатывают UI. Coop не получает
solo-профиль и остаётся PAUSED.

HTML-форма показывает подтверждённое имя в HUD через textContent. Черновик
не перезаписывается фоновыми snapshots; смена соединения отменяет применение
старого ответа. Фокус в поле сбрасывает удерживаемое движение, спринт и цель;
клавиатурный ввод в форму не становится игровыми командами.

## 14. Подтверждённая анимация атаки (T024)

LocalWorldMelee создаёт melee-action только для разрешённой атаки, включая промах.
Room отправляет событие всем сессиям игрока на том же шаге и не воспроизводит
историю при подключении. WorldConnection валидирует идентичность и монотонность
тика. MeleeAnimation — локальные фазы подготовки/удара/возврата с длительностью
из content; она не предсказывает урон и не разрешает команды. Scene рисует взмах
или выпад относительно текущей позиции и прицела; смена оружия, disconnect и
shutdown прерывают эффект. Баланс, порядок боевых систем и геометрия не меняются.

## 15. Обратная связь результата атаки (T025)

LocalWorldZombie.damage возвращает фактически снятые HP и признак убийства;
повторное попадание в уже удалённую цель возвращает null. LocalWorldMelee добавляет
необязательный impact к melee-action после урона. Это аддитивное расширение T024:
старые события без impact остаются допустимы и не порождают эффекты попадания.
Scene рисует краткую реакцию живой цели, кольцо и подпись промаха/урона/убийства
по событию, без вывода из удаления zombie-state. MeleeFeedback дедуплицирует
тики и очищает эффекты через 700 мс, при выгрузке чанка и разрыве жизненного цикла.

## 16. Устойчивый лут и инвентарь (T026)

[ADR 0003](adr/0003-durable-item-location.md) добавляет SQLite v3: item_location
в solo_world атомарно хранит единственный существующий бинт на земле или в сетке.
Saved-item явно проверяет и преобразует запись БД в доменную ItemLocation.
Неподдерживаемый ID/тип, чужой владелец, неправильная ячейка и неоднозначное
местонахождение останавливают загрузку без сброса. v1/v2 мигрируют транзакционно;
их несохранённый лут не восстанавливается, прежний бинт инициализируется один раз.

LocalWorldPickup на шаге готовит невидимый pendingSave. Room через setImmediate
после шага выполняет синхронный FULL commit, затем на следующем шаге Pickup
применяет готовый результат. До commit snapshots содержат старое состояние.
Команды во время записи остаются ограниченными Map по сессиям и повторно
валидируются после применения. Сбой запрещает новые шаги и останавливает хост;
shutdown/dispose не позволяют отложенному callback писать в закрытую БД.
Сетевой pickup-state/inventoryVersion=1, генератор и кооператив не меняются.

## 17. Экземпляры оружия и руки (T027)

Item.kind расширен четырьмя melee-видами; ItemLocation получил hands с playerId.
Правила playerInventory/playerHands/transferWeapon и однократная раскладка
addStarterWeapons находятся в simulation; размеры/масса в content. Обмен
проверяет владельца/источник, сначала освобождает выбранную ячейку, затем
размещает прежнее оружие. Отказ возвращает прежнее состояние без мутации.

SQLite v4 заменяет содержимое item_location массивом ровно пяти известных
экземпляров (бинт и четыре стартовых оружия). v3 преобразуется внутри прежней
EXCLUSIVE-транзакции; v1/v2 сначала проходят миграции T022/T026. Сохранение
проверяет уникальность ID, владельца, единственные руки, сетку и массу вместе;
частичная/повреждённая запись не восстанавливает набор молча. См. расширение
[ADR 0003](adr/0003-durable-item-location.md).

LocalWorldPickup владеет сеткой и руками; прежний pendingSave/commit/publish
теперь охватывает весь массив. LocalWorldMelee больше не хранит выбор оружия:
читает только подтверждённые руки через адаптер и сохраняет nextAttackTick
независимо от смены. Порядок шага не меняется. Клиент получает inventoryVersion=2
и meleeVersion=3; визуальный kind берётся из melee-state, команды передают itemId.
Coop остаётся PAUSED, его прежний набор и предметы живут только в памяти процесса.

## 18. Мировой лут оружия (T028)

Content задаёт четыре редких sites конечного loot-v1; worldgen выдаёт неизменяемый
manifest с устойчивыми ID и доступными seed-позициями. Отдельный overlay не меняет
террейн/препятствия generator v1. SQLite v5 однократно добавляет его к проверенному
старому набору, затем хранит все девять местонахождений без повторного spawn.
Миграция и ограничения описаны в [ADR 0003](adr/0003-durable-item-location.md).

LocalWorldPickup публикует ближайший groundItem в радиусе 8 м и проверяет подбор
по геометрии окрестности реальных чанков. Существующие правила сетки/массы и
pendingSave/commit/publish сохраняются. HTML/Scene используют имя и позицию
фактического предмета; выбор экземпляра в сетке задаёт itemId для экипировки.
Сетевые DTO и версии не меняются. Новый manifest добавляется только в solo-store;
кооператив остаётся PAUSED, его in-memory поведение не расширяется.

## 19. Устойчивое здоровье и cooldown (T029)

SQLite v6 добавляет combat_state: HP игрока и оставшиеся шаги melee-cooldown.
[ADR 0004](adr/0004-durable-combat.md) определяет восстановление и подтверждения.
LocalWorldCombat получает сохранённые HP; LocalWorldMelee восстанавливает
nextAttackTick относительно нулевого tick нового процесса. Сохраняемый остаток
не зависит от выбранного оружия, абсолютного времени и старого номера шага.

Room вычисляет бой после движения/предметов и до публикации. Изменение HP,
принятый удар/промах и каждое уменьшение cooldown требуют синхронного FULL commit
из setImmediate вне timestep; до commit следующий шаг блокируется, затем
публикуются его snapshots и action. Одновременные item_location/combat_state
записываются одним UPDATE. Подтверждённые руки по-прежнему активируются на
следующем шаге. Shutdown завершает подготовленную запись ровно один раз;
ошибка записи прекращает шаги/таймер и останавливает хост без публикации результата.

Без вкладок cooldown идёт на фиксированных шагах хоста; остановленный процесс
не симулирует бой. v1–v5 получают исходные 100 HP/0 шагов однократно внутри
миграции, остальной мир/вещи/профиль сохраняются. Невалидные HP/остаток v6
отклоняются без восстановления значений по умолчанию. Зомби и их атаки, stamina,
смерть и раны на диск не добавлены. Coop остаётся PAUSED. Стоимость fsync до
20 раз/с во время cooldown — ограничение текущего solo-среза, без нагрузочной приёмки.

## 20. Кровотечение (T030)

Domain задаёт BleedingState с bleedingTicks: 0 — без раны, 1–100 — остаток до урона.
Content задаёт предварительный баланс: шанс 0.25 при нелетальном ударе зомби,
1 HP/100 шагов. Чистые stepBleeding/woundFromZombieHit получают состояние и
явный roll; Math.random находится только в серверном адаптере и подменяется
детерминированным источником в тестах. Повторная рана не складывается и не
сбрасывает остаток. После melee идут существующие раны, затем атаки зомби;
новая рана получает полный интервал. При 0 HP рана заморожена до будущего lifecycle.

LocalWorldCombat хранит рану по playerId и обрабатывает её ровно раз за шаг,
включая отсутствие вкладок. SQLite v7 расширяет combat_state: bleedingTicks
сохраняется вместе с HP/cooldown и одновременными вещами до любой публикации.
v1–v6 мигрируют внутри прежней транзакции; существующие HP/cooldown v6
проверяются и сохраняются, новая рана не создаётся. Повреждённый v7 отклоняется
без сброса. Штатный shutdown и сбой записи сохраняют гарантии T029.

HealthVersion=2 передаёт рану HUD; монотонный tick/room guard остаётся общим
с HP. Клиент не симулирует рану. Остановленный хост не тикает и wall-clock
не использует. Лечение/смерть — T031/T032; кооператив остаётся PAUSED.
Как в T029, каждый активный интервал требует до 20 FULL commit/с; нагрузочное
измерение не выполнено. См. [дополнение ADR 0004](adr/0004-durable-combat.md).

## T031 — использование бинта

Чистая useBandage из simulation проверяет конкретный предмет в контейнере живого
раненого игрока. LocalWorldPickup сериализует команду в прежней очереди действий,
LocalWorldCombat владеет раной. Порядок предметы/бинт → melee → кровотечение →
атаки зомби позволяет остановить последний периодический урон, но не предотвращает
новую рану от последующего удара. HP не восстанавливаются.

SQLite v8 допускает отсутствие расходованного бинта при полном манифесте оружия;
v1–v7 проверяются строго до миграции. Один UPDATE сохраняет расходование и рану
до публикации всего шага. После commit pickup сразу публикует новое содержимое,
чтобы вещи и рана подтверждались одним tick. Подробности —
[ADR 0004](adr/0004-durable-combat.md). UI использует существующие snapshots;
лечение союзников, анимация перевязки, смерть и новые предметы не добавлены.

## T032 — смерть игрока

PlayerLifeState (`alive`/`dead`) однозначно выводится из авторитетных HP:
положительные HP означают жизнь, 0 — смерть. Нет второго mutable-флага и
повторного события смерти. Старые SQLite v8 с 0 HP уже означают умершего игрока;
формат сохранения и миграции не меняются. HealthSnapshot v3 проверяет согласованность
lifeState и HP; клиент и хост нужно пересобирать вместе.

Движение проверяет HP перед применением намерения, очищает WASD/цель/спринт/скрытность
и шум умершего. Подбор, перенос в сетке, экипировка, атака и бинт отклоняются
на сервере даже при прямой отправке команд. Очередь действий сохраняет прежний
порядок: движение → вещи/бинт → melee → кровотечение → зомби. Действия живого
в начале смертельного шага допустимы; после боевого расчёта режим движения
сбрасывается до публикации. Оба источника урона насыщают HP на нуле.

Первый переход к 0 HP сохраняет также конечную позицию в том же UPDATE, что HP
и одновременные вещи. Отказ записи останавливает хост без snapshots этого шага.
Поздние команды не оживляют игрока. Клиент ждёт первого health-state перед
разрешением ввода; смерть очищает историю предсказания и цель, отключает кнопки,
останавливает анимацию оружия и показывает экран смерти. Disconnect скрывает экран
до нового подтверждения. Вещи остаются за персонажем, тела и возрождения пока нет.

## T033 — тело и контейнер после смерти

SQLite v9 добавляет corpses: устойчивый corpseId, playerId, конечную позицию и
серверное diedAtMs. ItemLocation получает владельца corpse. Первый переход HP к
нулю переносит сетку и руки, включая изменения текущего шага, в одно тело.
Тело, вещи, HP и позиция фиксируются одним FULL UPDATE до публикации; отказ
останавливает хост. Загрузка v1–v8 атомарно мигрирует старого умершего с вещами
в тело; последующая загрузка сохраняет ID и не выдаёт вещи повторно.

PickupSnapshot v2 аддитивно передаёт проверяемый corpses со списками вещей
ближайших тел; старые snapshots без поля допустимы. Клиент показывает маркер
тела и кнопки конкретных экземпляров. Подбор использует общий переход
pickUpItem: живой получатель, 1,5 м, достижимость без стены, свободная сетка и
масса. Место хранения меняется только после commit, повторный подбор безопасен.
Тела сохраняются независимо от загруженных чанков. Возрождение и срок тела —
T034/T035; кооперативная приёмка остаётся PAUSED.

## T034 — явное возрождение и поколения команд

Solo-профиль сохраняет playerId и имя; новая жизнь получает следующий lifeRevision.
Номер хранится в combat_state SQLite v9 как проверяемое опциональное поле: старые
сохранения без поля означают жизнь 0. Отдельной миграции колонок не требуется.
Возрождение допустимо только при 0 HP, с ожидаемым номером жизни и после переноса
вещей в тело. HP 100, отсутствие раны/cooldown, стартовая позиция и новый номер
фиксируются одним FULL UPDATE. До успешной записи клиент не видит новую жизнь.
Сбой останавливает хост; повтор или запрос второй вкладки не создаёт ещё одну жизнь.

Детерминированный поиск у старта исключает препятствия, позиции других игроков
и дистанцию атаки известных зомби с запасом 1 м. После commit сбрасываются ввод,
очереди вещей/атак, выносливость и таймер атак по прежней жизни. Стартовый набор
не выдаётся; прежние тела и профиль не меняются. Перезагрузка сама не возрождает.

HealthSnapshot v3 аддитивно передаёт lifeRevision. Клиент запоминает подтверждённый
номер и добавляет его ко всем игровым командам; сервер отсекает старые поколения.
Отсутствующий номер принимается только в первой жизни 0. Имя относится к профилю
и не зависит от поколения. После подтверждённой смены жизни UI сбрасывает prediction
и старую цель. Хост и клиент нужно пересобирать вместе; старый клиент после
возрождения новой версией должен обновиться. Кнопка возрождения явно запускает
переход, а сетка и руки остаются пустыми до подбора вещей с тела.

## T035 — 24 реальных часа для тела

corpseSettings задаёт 24 часа. Тело получает абсолютный expiresAtMs от серверного
времени смерти; время не тикает на клиенте. Старый corpse без поля получает
дедлайн из прежнего diedAtMs, а не из времени загрузки. Нормализация метаданных
и удаление уже истёкших тел выполняются внутри начальной транзакции SQLite v9.
Срок учитывает остановку хоста и выгруженные чанки.

Перед игровыми действиями шага очистка подготавливает новый список тел и вещей.
Ровно на границе expiresAtMs контейнер уже нельзя открыть или подобрать;
дополнительная проверка времени стоит непосредственно перед переносом. Остатки
тела и здоровье/смерть текущего шага сохраняются одним FULL UPDATE до публикации.
При отказе записи хост останавливается. Повтор очистки безопасен; предмет,
подобранный до дедлайна, остаётся у получателя.

Удалённый предмет исчезает из всех игровых контейнеров и snapshots. В конечном
манифесте остаётся только location типа expired с известным ID/kind: это метка
удаления, предотвращающая повторное появление лута и позволяющая по-прежнему
отклонять повреждённые сохранения с пропавшим или неизвестным оружием. Такие
записи нельзя подобрать или экипировать; тело больше не хранится. Новых колонок
и ослабления проверки полноты манифеста нет. Хост/клиент пересобираются вместе.
Изменение часов компьютера и восстановление мирового лута остаются вне scope.

## T036 — пистолет и магазин экземпляра

Item получает вариант pistol с rounds и magazineCapacity. copyItem копирует
состояние без позиции земли/ячейки; подбор, сетка, руки, тело и метка удаления
сохраняют ID и магазин. Пистолет занимает 2 × 1 ячейки и 800 г; ёмкость 8 патронов
9 мм. Подтверждённый HUD показывает N/8, в руках виден отдельный силуэт.
Экипировка использует существующий единственный слот и проверки массы/сетки;
пистолет не выполняет melee-удары. Состояние экипировки допускает WeaponId,
анимация melee остаётся только для четырёх прежних видов оружия.

SQLite v10 добавляет ровно один pistol-v1 overlay к строго проверенному старому
манифесту. Новый пистолет начинается с полным магазином; текущее состояние затем
сохраняется без пополнения при смене оружия/reload/рестарте. Старая геометрия,
seed и четыре melee loot-v1 не меняются. Пистолет выбирает доступную точку рядом
с первым loot-site; его ID стабилен, редкость — один экземпляр против четырёх
мировых melee-предметов. Ошибка миграции откатывает манифест и версию вместе.
Повреждённые патроны/ёмкость и потерянный экземпляр отклоняются; expired-пистолет
не выдаётся заново. Сетевые item/equipment DTO расширены, хост и клиент нужно
пересобрать вместе. Выстрел и перезарядка — T037/T038; кооператив PAUSED.

## T037 — серверный одиночный выстрел

Пистолет передаёт только itemId, ожидаемую weaponRevision и конечное ненулевое
направление прицела, вместе с актуальной lifeRevision. Урон/цель/позицию клиент
не задаёт. Чистая tracePistolShot нормализует направление, пересекает луч 20 м
с AABB препятствий и окружностями зомби радиуса 0,35 м; ближайшее пересечение
побеждает, при равенстве — стена. Проверяются известные цели в дальности луча,
включая зону 18–20 м за пределами радиуса преследования. Баллистики/PvP нет.

LocalWorldFirearm исполняется после melee и до повреждения игрока. Оба типа
атак используют общий сохранённый cooldown. Принятый выстрел, включая промах,
списывает патрон и увеличивает необязательную revision экземпляра (старый
предмет = 0). Сравнение ревизии делает retry безвредным после паузы и рестарта.
copyItem, wire validation и SQLite v10 сохраняют/проверяют токен; схема прежняя.
Списание по ID обновляет staged location, поэтому одновременная смена оружия
или смерть сохраняет уже уменьшенный магазин. Item state и cooldown проходят
один FULL UPDATE до публикации shot-action и snapshots; отказ останавливает хост.
HP/популяция зомби остаются непостоянными, как в T029.

ПКМ, пробел без autorepeat и кнопка HUD отправляют одно действие; ввод имени
не стреляет, ЛКМ остаётся движением. Клиент использует подтверждённый itemId и
revision. Отдельный shot-action сообщает реальный урон/исход и точки луча.
Эффекты ограничены по числу/времени, дубли ревизии и старые тики отбрасываются,
смерть/разрыв очищают их. Звуковое привлечение и перезарядка — T039/T038.

## T038 — патроны и перезарядка

AmmoStack хранит количество 9 мм; пачка до 8 патронов занимает 1×1, каждый
патрон весит 12 г. itemWeightGrams и itemDisplayName учитывают количество во
всех местах инвентаря, подбора и тела. Новый конечный overlay размещает одну
пачку в проверенной доступной точке пистолета. SQLite v11 читает отдельные
манифесты старых версий и атомарно добавляет отсутствующий слой один раз.
Исходный генератор/ID melee и пистолета прежние. Израсходованная пачка остаётся
consumed-меткой известного ID с quantity=0: она не занимает сетку и не появляется
снова. В остальных местах допустимо только 1–8; пачка не может находиться в руках.

reloadPistol переносит лишь существующие патроны из принадлежащих игроку пачек
в сетке, до ёмкости 8. Количество пачки и магазин/ревизия пистолета меняются одной
операцией сохранения; частичный остаток сохраняет ID/ячейку, нулевой — consumed.
Неизвестный/неподходящий предмет, полный магазин, отсутствие пачки, неверная
ревизия не расходуют ничего. Детерминированный порядок пачек — по itemId.

LocalWorldReload держит временный таймер 40 фиксированных шагов (2 с), общий
для вкладок игрока. prepare после предметных команд блокирует стрельбу; finish
после повреждения игрока проверяет здоровье и staged hands. Поэтому смерть
или успешная смена оружия даже на завершающем шаге отменяет действие без расхода.
Отклонённая экипировка его не прерывает. Повторы не сбрасывают таймер; завершение
увеличивает revision оружия, делая старый retry безвредным. Только после FULL
UPDATE клиент получает наполненный магазин/остаток пачки. Ошибка останавливает
хост без публикации половины переноса. Промежуточный прогресс не записывается в SQLite:
перезапуск отменяет её без расхода. Если в шаге мира нет подключённого
персонажа, таймер снимается; одна оставшаяся вкладка продолжает его. Graceful shutdown может завершить уже подготовленный commit.

R без autorepeat/ввода имени и кнопка HUD посылают намерение с подтверждёнными
itemId/revision/lifeRevision. Проверяемый firearm-state передаёт оставшиеся шаги
для индикатора и блокировки кнопок; сервер повторно проверяет все ограничения.

## T039 — распределённое оружие и реакция зомби

По подтверждённому пожеланию пользователя обычное обнаружение — 6 м, сохранение
цели — до 12 м. Рендер отделён от агро: visibilityRangeMeters остаётся 22 м, а
дальность пистолета — 20 м. Стены по-прежнему блокируют зрение. Умершие и
отключённые игроки не являются живыми целями; подключённое представление тела
может поддерживать загрузку чанка. До обнаружения зомби за 6 м остаётся спокойным.

Новый конечный overlay scatter-v1 добавляет шесть доступных точек в стартовой
области: четыре melee-оружия и два пистолета с отдельными пачками по 8 патронов.
Якоря распределены по четырём направлениям; ограниченный поиск свободной точки
по существующей геометрии детерминирован для seed. Старые terrain/loot слои и
ID не меняются. SQLite v12 сначала проверяет старый манифест соответствующей
версии, затем атомарно добавляет только новые ID. Всего 19 конечных предметов
включая четыре стартовых и бинт (18 после расхода бинта). Собранные экземпляры,
магазины, пачки, тела и tombstone-метки не регенерируются. Отказ миграции откатывает
весь файл. Существующий выбор экземпляра по ID позволяет менять два пистолета
одного типа с разным боезапасом; успешная такая замена тоже отменяет перезарядку.

Принятый и сохранённый выстрел создаёт сигнал AI радиусом 24 м с интересом на
200 шагов (10 с). Room передаёт acceptedShots в LocalWorldZombie один раз до
рассылки клиентам, после успешного FULL UPDATE. Пустой магазин, cooldown, старый
retry или отказ commit не создают сигнал. На каждый itemId запоминается наибольшая
ревизия выстрела; повтор не продлевает срок. Дедлайн считается от исходного тика,
а не времени доставки. Шум проходит стены; движение к услышанной точке использует
тот же обход препятствий, скорость и стоп-дистанцию, что обычное преследование.

Сначала проверяется реальная живая цель. Если её нет, зомби с активным интересом
идёт к слышимой точке с targetPlayerId=null: фиктивный игрок не создаётся, ударить
по отсутствующему персонажу нельзя. При появлении игрока в зрении начинается
обычное преследование. Срок, смерть зомби и выгрузка чанка очищают интерес;
зомби вне загруженных чанков не двигаются. Повтор после выгрузки не оживляет
старый сигнал. Память интереса и популяция зомби остаются временными (T029);
новая система слуха для движения, аудиодвижок и дальняя симуляция не добавлялись.

## T039A — оружие и патроны в каждом посещаемом чанке

По уточнённому поручению пользователя каждый чанк 64×64 м при первом посещении
должен иметь оружие и пачку 9 мм. Чистый generateChunkLoot задаёт слой
chunk-loot-v1 с ID по целочисленным координатам чанка, детерминированным видом
оружия и свободной точкой в центральных проходах. Пистолет — один из пяти
вариантов, с прежним магазином 8; пачка — прежние 8 патронов. Террейн, геометрия,
старые ID и их состояния не меняются. В (0,0) уже есть оба типа старых слоёв,
поэтому новый слой пуст; в трёх соседних чанках со старым melee добавляется
только пачка рядом с ним. Новая пачка смещена на 2 м от оружия, чтобы её можно
подобрать отдельно при почти полной сетке и уже имеющемся пистолете: UI
предлагает ближайший предмет. Собранный/утраченный старый экземпляр тоже считается
уже созданным: правило не поддерживает вечный минимум лута на земле.

Solo Room рассматривает фактически занятый живым игроком чанк, а не все девять
подгруженных соседей. После предметных команд добавляет отсутствующие ID к
staged locations; подтверждённые, consumed и expired ID повторно не создаются.
Шаг заморожен до прежнего deferred FULL UPDATE; предметы и движение не
публикуются до успешного commit. Смерть, expiry, экипировка и стрельба сохраняют
тот же общий порядок. Чекпойнт обычного движения остаётся периодическим.

SQLite v13 добавляет loot_chunks — независимый JSON-реестр ожидаемых ключей
чанков. Он хранится в той же строке, что item_location. Серверный Store выводит
из новых корректных ID добавленные ключи, проверяет полный ожидаемый набор
предметов и пишет реестр/вещи вместе (с HP/телом, если они изменились). Только
после успешного UPDATE обновляется память манифеста. Частичная регистрация,
пропавшие/дублированные записи, неправильный вид/позиция/метаданные, неканоничные
или неподдерживаемые координаты отклоняются. Пустой магазин, частичная/consumed
пачка и expired-оружие остаются теми же экземплярами после reload/restart.

Миграция v12 сначала проверяет прежний полный манифест и добавляет пустой
реестр без выдачи новых вещей; v1–v11 проходят прежние слои последовательно.
Ошибка откатывает схему и данные вместе. При старте v13 ожидаемые новые предметы
вычисляются из реестра, поэтому потерянная запись не маскируется регенерацией.
Ограничение размера JSON вещей растёт линейно с известным манифестом; прежняя
нижняя граница 16 KiB сохраняется. Поиск спавнов при валидации индексирован по
ID, чтобы большой посещённый мир не требовал квадратичного числа сравнений.
Wire DTO и клиентский интерфейс используют прежние команды/пачки/перезарядку.
Coop PAUSED; восстановление собранного лута и нагрузочная ёмкость вне scope.

## T041: отображение персонажей

CharacterVisual владеет одним Container/Graphics на персонажа; BootScene создаёт
и удаляет фигуры по видимым ID. CharacterMotion — чистая локальная презентация
с явными позицией и deltaMs: шаг от расстояния, затухание, дыхание и reset.
Игрок использует прежнее предсказанное положение без дополнительного lerp.
Зомби и другие персонажи сглаживаются между снимками только в рендере; большие
переносы/длинный кадр сбрасывают переход. Raw-снимки, мир и коллизии неизменны.
Рука преобразуется из фактической позиции/угла оружия с учётом crouch scale;
начало оружия и серверно подтверждённая MeleeAnimation сохраняются.
lifeState управляет видимостью живой фигуры, независимо от сохранённых координат
для камеры: смерть/отключение сбрасывают позу, возрождение начинает idle.
Визуальные объекты удаляются при выгрузке; Phaser освобождает display list при
shutdown, адаптер очищает ссылки и карты. Новых таймеров, IO, протокола, polling
или зависимостей нет. Детали приёмки — [CHARACTER_VISUALS.md](CHARACTER_VISUALS.md).

## T042: состояние боя

LocalWorldCombat считает остаток в фиксированных шагах хоста: принятый melee-удар
или выстрел, включая промах, а также фактическая потеря HP устанавливают 200 шагов
(10 секунд). Повторное событие начинает интервал заново. Непринятые команды его
не меняют; при возрождении он очищается. HealthSnapshot v4 передаёт остаток,
клиент только показывает «В бою» при положительном значении у живого игрока.
Без вкладок таймер продолжает идти, пока хост работает. В T042 он ещё не хранится
в SQLite; сохранение остатка для рестарта входит в T045.

## T046: сохранение здоровья зомби

SQLite v14 добавляет `zombie_health` к строке одиночного мира. JSON хранит только
стабильные ID зомби с HP ниже полного значения: 0 означает гибель. При загрузке
проверяются формат ID, канонические координаты чанка/ячейки, отсутствие дублей и
целые HP в диапазоне 0–99. Старые сохранения получают пустой реестр в той же
транзакции миграции; повреждённое сохранение отклоняется без сброса мира.

`LocalWorldZombie` восстанавливает здоровье до первого заселения чанков, не
создаёт убитых и сохраняет раны при повторном посещении. Room включает изменённый
реестр в тот же FULL UPDATE, что состояние боя, расход патронов и вещи; публикация
удара/выстрела следует после успешной записи. Позиции и цели остаются временными,
их восстановление — T047. Протокол и клиент не меняются.

### Позиции зомби (T047)

SQLite v15 хранит реестр `zombie_positions`: стабильный ID и координаты всех
двигавшихся зомби. Каждое изменение позиции записывается до публикации snapshot
в том же FULL commit, что HP и результат боя. При восстановлении эти ID создаются
до заселения чанков; исходный чанк пропускает уже восстановленных и убитых.
Без игроков AI остаётся неподвижным, цели и слух после рестарта сбрасываются.
Миграция v14 добавляет пустой реестр без изменения прежнего мира.

### Общий вес снаряжения (T048)

`equipmentWeightGrams` в simulation суммирует предметы сетки, рук, патроны
в пачках и магазинах. HUD использует подтверждённый pickup snapshot; перенос
оружия сохраняет итог, выстрел убирает 12 г, бинт — 100 г. Сетевой контракт
и сохранения прежние. Лимит размещения контейнера 2000 г сохраняет прежние
правила: масса предметов и пачек без учёта заряженных патронов; новый общий
вес отдельно учитывает весь боезапас и не является лимитом переносимого груза.

### Нагрузка и спринт (T049)

Сервер перед шагом движения вычисляет полный вес подтверждённых вещей и
передаёт `carriedWeightGrams` в состоянии игрока и peers. Это необязательное
добавление к v5: отсутствие означает нулевой груз, некорректное значение
отклоняется. Ввод клиента не задаёт массу. Оба транспортных адаптера копируют
поле, предсказание использует тот же общий шаг и вес из snapshot.
Расход спринта умножается на `min(3, 1 + вес / 2000 г)`: стартовые 1900 г
дают ×1,95, без груза — ×1. Скорости, восстановление и скрытность прежние.
Смена вещей влияет на движение со следующего шага после commit. HUD показывает
вес и множитель до спринта. Баланс задан в content и предварителен.

### Часы мира (T050)

`stepWorldClock` в simulation прибавляет 3000 игровых мс за фиксированный
шаг 50 мс. Начало суток — 08:00, масштаб — 60 игровых секунд за реальную
секунду при 20 Гц; сутки длятся 24 игровых часа. Room работает без клиентов,
часы идут вместе с симуляцией и не используют календарь или время браузера.
Остановка хоста приостанавливает отсчёт; прошедшее вне процесса время не добавляется.

SQLite v16 хранит `world_time_ms`, миграция v15 добавляет ноль без смены
мира, персонажа или вещей. Checkpoint позиции раз в секунду и shutdown
сохраняют часы; commit боя/вещей записывает их атомарно. При SIGKILL возможен
откат до последнего checkpoint (обычно до одной секунды хоста, при задержке
цикла дольше). Реальные 24 часа существования тела остаются отдельным сроком.

Необязательное поле `MovementSnapshot.worldTimeMs` дополняет v5; валидатор
принимает неотрицательный safe integer, reader сохраняет ноль. Оно присутствует
уже в раннем запросе состояния и затем в snapshots. HUD форматирует «День · HH:MM»;
legacy snapshot и disconnect показывают «—». Coop держит часы в памяти;
его постоянное хранение остаётся вне одиночного этапа.

### Таймер точки лута (T051)

Устойчивый ID исходного предмета manifest служит ID точки. Наличие этого
экземпляра на земле, включая неполную пачку, означает занятый запас.
После полного сбора общий шаг назначает срок `worldTimeMs + 6 игровых часов`.
Повторная проверка пустой точки не сдвигает срок. SQLite v17 добавляет
`loot_restocks`; legacy пустая точка получает срок при первом шаге хоста.

LocalWorldLootTimers разделяет staged и committed карты. Изменение срока,
вещи и часы сохраняются атомарно до публикации; ошибка прекращает хост.
Ранний RPC также читает только committed карту. После reload/restart срок
сохраняется. Необязательное `PickupSnapshot.restocks` содержит до 128 точек
в радиусе видимости, ближайшие первыми; pointId не является новым экземпляром
вещи. HUD показывает название и абсолютный срок по часам мира. Валидатор
отклоняет повторы ID, неизвестный kind и некорректные координаты/сроки.

Период предварительный: 6 игровых часов соответствуют 6 минутам работающего
хоста при текущем масштабе. Генерация новой пачки после срока — T052;
до неё истёкший срок остаётся метаданными. Co-op остаётся без этих solo-таймеров.

### Пополнение патронов (T052)

В срок пустая точка 9 мм рядом с игроком получает одну пачку. ID экземпляра —
`<pointId>:restock:<deadline>`, исходный ID точки не зависит от владельца вещи.
Частичный остаток исходной или новой пачки занимает точку и снимает таймер.
После полного сбора новой пачки назначается новый срок от текущих часов.
Пропущенные периоды не накапливают запас. Оружие и бинт пока не пополняются.

В общем шаге создаётся staged запас; новый предмет, снятие таймера и часы
сохраняются до отправки snapshots/RPC. SQLite v18 сохраняет все прежние вещи
и новые пачки, проверяет канонический ID, исходную точку, позицию, количество,
полноту исходного manifest и единственный наземный запас точки.
Миграция v17 не создаёт вещей. Постоянные solo-данные не расширяют co-op.
Пополнение выгруженных районов относится к T053.

### Припасы в выгруженных чанках (T053)

Реестр точек живёт отдельно от активного окна местности и AI. Каждый шаг
проверяет все ранее зарегистрированные точки, даже без клиентов. Новые
непосещённые чанки не генерируются ради таймеров. Пропущенные периоды дают
один текущий запас; повторная загрузка чанка не сбрасывает таймер/экземпляр.
Унесённые вещи, в том числе в теле, учитываются отдельно от запаса точки.
Сохранение и барьер публикации те же, что в T052, новая схема БД не нужна.

### Фазы освещения (T054)

Общая `getDaylightPhase` выбирает фазу из сохранённого `worldTimeMs` с учётом
начала в 08:00 и 24-часового цикла. Предварительные границы в content:
рассвет 05–07, день 07–18, сумерки 18–20, ночь 20–05. Phaser WorldLighting
накладывает свой оттенок и прозрачность на игровое поле; HTML HUD остаётся
поверх него. Фаза не имеет собственного browser-таймера или persistence.
Ранний snapshot, обычные обновления и restart используют одни часы.
Отсутствующий clock/disconnect очищает освещение, shutdown освобождает graphics.
Ограничение дальности в темноте — отдельная T055, луч — T056.

### Дальность обзора (T055)

Общий `isPositionVisible` задаёт радиальный обзор по фазе: 22/12/8/3 м
для дня/рассвета/сумерек/ночи. Клиент применяет его к интерполированным
персонажам, мировому предмету, телам и feedback боя. Подсказки/кнопки используют
то же правило; переход фазы или подход меняет сцену и UI в одном кадре.
Проверки дальности и допустимости действий на хосте остаются прежними.
Legacy clock-less snapshot сохраняет дневной диапазон; без observer всё скрыто.
Это presentation visibility: сетевые snapshots по-прежнему содержат разрешённые
прежним протоколом сущности и не обеспечивают сокрытие от отладчика браузера.
Фонарик расширяет область обзора в T056, стены перекрывают свет в T057.

### Фонарик (T056)

Фонарик — локальный инструмент обзора, L или кнопка HUD. Направление берётся
из того же прицела мыши, что оружие; конус 60° расширяет обзор до 12 м.
`isWithinFlashlightAngle` общий для видимости сущностей и визуального конуса,
угол нормализуется через sin/cos, включая границу ±π. Ближний обзор остаётся
по фазе суток. В темноте WorldLighting рисует дополнение круга/конуса
трапециями, оставляя освещённую область без затемнения; отдельная текстура
или renderer-specific инверсия маски не нужны. Graphics переиспользуется.

Состояние по умолчанию выключено, не хранится на хосте и не передаётся peers.
Смерть, disconnect и reload выключают инструмент. Text focus, модификаторы
и repeat не вызывают переключения; HUD показывает состояние через aria-pressed.
Проверки подбора/боя остаются серверными. Стены/перекрытие луча — T057;
в этой задаче свет проходит через них.

## T058–T059 — погода и туман

Погода — общая чистая функция сохранённого worldTimeMs из snapshot. Время
пустого работающего хоста уже движется; новое поле БД или сетевое сообщение
не требуется. В 48-часовом цикле с 24-го до 40-го часа туман, вне него
сохраняется дождь с 4-го до 8-го часа каждого 12-часового периода.

getVisibilityRanges возвращает общие расстояния для видимости сущностей
и отрисовки света/дымки: в туман обычный обзор ограничен 8 м, фонарик 6 м;
ночной ближний круг остаётся 3 м. Непрозрачная дальняя дымка скрывает также
местность и ориентиры. Лучи используют геометрию стен T057. Graphics дождя
и освещения переиспользуются, очищаются при disconnect и удаляются при
shutdown. Игровой UI остаётся HTML поверх canvas.

## T060 — бинт в заброшенном медпункте

Медпункт — аддитивный визуальный ориентир в руинах чанка (1, 0): пол, обломок
крыши и медицинский знак. Южный вход использует существующий разрыв стен;
геометрия генератора v1 не меняется и не блокирует прежние сохранённые позиции.
`generateChunkLoot` добавляет устойчивую точку `chunk-loot-v1:1:0:bandage`
при первом посещении. SQLite v19 добавляет её ровно один раз только в уже
зарегистрированный чанк медпункта; прежние вещи/таймеры остаются прежними.

Пополнение использует общий срок 6 игровых часов и отдельный ID экземпляра,
как патроны. Использованный бинт этого медпункта остаётся непригодной записью
`consumed` в полном manifest. Она не отправляется в инвентарь, не оживает при
загрузке и позволяет проверять полноту сохранения. Legacy starter-bandage
сохраняет прежнее поведение удаления после использования. Унесённые и новые
экземпляры не подменяют друг друга; пропущенные периоды не копят наземный запас.

## T085–T086 — постройки и запас военного склада

Склад в участке (0, −1) и мастерская в (−1, 0) используют проходимые полы
и существующие стены генератора v1. Карта показывает постройки по тем же
записям посещений, что и рельеф.

Первое посещение склада в solo добавляет к обычному луту участка два
пистолета и две пачки патронов со стабильными ID. Схема SQLite v20 добавляет
запас только для уже посещённого склада и проверяет прежний манифест до записи.
Список зарегистрированных участков и местоположения предметов сохраняются
в одной операции. Патроны пополняются по существующим правилам точек лута.

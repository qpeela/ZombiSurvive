# Архитектура ZombiSurvive

Статус: принятая основа проекта. Изменения границ оформляются отдельным
архитектурным решением и PR. Этот файл определяет техническую архитектуру;
[GAME_DESIGN.md](../GAME_DESIGN.md) определяет игровые требования.
[CODE_STYLE.md](CODE_STYLE.md) определяет правила кода.

## 1. Выбранный подход

Модульный монорепозиторий на TypeScript. Один сервер симуляции владеет одним миром.
Браузерный клиент отображает разрешённое ему состояние и отправляет намерения игрока.
Сервер запускается на компьютере игрока-хоста. Одиночная игра и кооператив
с друзьями используют одну серверную симуляцию; отдельный платный хост не требуется.
Решение: [ADR 0001 — локальный хост и кооператив](adr/0001-local-host-coop.md).

Игровая логика отделена от Phaser, транспорта, БД и интерфейса.
Цель — небольшая группа друзей. Максимальная вместимость определяется по
измерениям на компьютере хоста; публичный мир на 100 игроков вне текущего scope.
Микросервисы, распределённый мир и отдельный ECS-фреймворк пока не вводятся.

## 2. Технологии

- Node.js 24; конкретная версия — .nvmrc. Пакетный менеджер — npm, один package-lock.json.
- TypeScript, ESLint flat config, typescript-eslint, Prettier и dependency-cruiser.
  Совместимые точные версии — package.json и lockfile.
- Клиент: Phaser 4.2.1 + Vite 8.3.4, зафиксированы в T001.
- Сервер: Node.js; HTTP health endpoint и Colyseus/WebSocket в T003:
  @colyseus/core 0.18.18, @colyseus/ws-transport 0.18.4, клиент @colyseus/sdk 0.18.5 (MIT).
  В одиночном режиме доступ только
  через loopback; кооператив явно разрешает доступ через выбранный сетевой интерфейс.
  Браузерный клиент и игровой endpoint обслуживает один локальный сервер.
  Для loopback используется HTTP/WS; защищённое подключение друзей описано в ADR 0001.
  С T005A `npm start` запускает собранный сервер и раздаёт клиент с того же origin;
  dev и preview используют Vite proxy. T003 создаёт один Room при старте процесса, запрещает
  клиенту создавать комнаты и сохраняет пустую комнату до остановки сервера.
  Все solo-вкладки получают одного персонажа, серверные worldId/playerId
  устойчивы до завершения процесса. T005B добавляет отдельные идентичности
  участников кооператива; cookie одного профиля браузера связывает его вкладки.
- Хранение первой версии: SQLite на компьютере хоста, очередь коротких транзакций.
  Хост владеет файлами общего мира, персонажами участников и локальными бэкапами.
- UI: HTML/CSS поверх игрового canvas. React/FSD пока не используются.
- Проверки запуска: Playwright 1.64.0, production-сборки клиента и сервера.
  Vitest 5.0.4 (MIT) проверяет игровую логику с T004; Vite 8.3.4 также
  закреплён в корне как его совместимый peer. Unit-тесты типизируются и проходят
  общий lint; vitest.config.mjs отделяет их от Node/Playwright-наборов.
  Проверки инфраструктурных ограничений используют Node test runner.

Не обновлять отдельный инструмент до latest без проверки диапазонов совместимости.
В текущем наборе TypeScript 6.0.3 совместим с typescript-eslint 8.71.2;
TypeScript 7 пока вне заявленного диапазона этого линтера.

## 3. Модули и единственное направление зависимостей

```text
apps/client       отрисовка, ввод, сетевой адаптер, UI и аудио
apps/server       игровой цикл, сетевой адаптер, доступ, БД и эксплуатация
packages/domain   общие игровые типы, ID, значения; без сетевых сообщений
packages/content  определения предметов, зомби, балансовые параметры
packages/protocol сетевые DTO, команды, события и версия протокола
packages/simulation движение, бой, AI, инвентарь, выживание
packages/worldgen генерация местности и локаций по seed
tools             проверки и служебные инструменты разработки
tests             интеграционные проверки и проверки инструментов
assets            источники ассетов и лицензии
docs              требования, правила и архитектурные решения
```

| Модуль     | Разрешённые зависимости на пакеты проекта       |
| ---------- | ----------------------------------------------- |
| domain     | Нет                                             |
| content    | domain                                          |
| protocol   | domain                                          |
| simulation | domain, content                                 |
| worldgen   | domain, content                                 |
| client     | domain, content, protocol, simulation, worldgen |
| server     | domain, content, protocol, simulation, worldgen |

Матрица для автоматической проверки: tools/architecture-policy.ts.
Все изменения матрицы одновременно отражаются в этом документе.

- Клиент и сервер не импортируют код друг друга.
- Общие пакеты не импортируют приложения, Node runtime, Phaser, Colyseus или БД.
- Runtime-зависимости общего ядра добавляются только через явное решение.
- Внешние пакеты доступны адаптерам приложений и тестам по назначению.
- Импорт другого пакета только через @zombi-survive/<name> и его src/index.ts.
  Межпакетные относительные импорты внутренних файлов также запрещены проверкой.
- Внутри пакета прямые относительные импорты разрешены; собственный index.ts
  не используют для импорта внутренних функций, чтобы не создавать циклы.
- src/index.ts экспортирует публичный API явно. Общего barrel на все пакеты нет.
- При создании пакета задать exports; конфигурацию разрешения workspace-импортов
  согласовать с TypeScript, Vite, Node и dependency-cruiser.

В T002 созданы domain и protocol; контракты — [MOVEMENT_PROTOCOL.md](MOVEMENT_PROTOCOL.md).
Публичные exports используют исходники при условии development, собранные JS
по умолчанию и декларации для TypeScript. Node dev включает это условие явно,
Vite использует его в development. Проверка графа также читает исходники.
С T004 созданы content и simulation; T011 добавляет worldgen. Корневые build/lint/typecheck сначала
собирают общие пакеты через build:core: domain → protocol → content → simulation → worldgen.
Команда build:contracts сохраняется для отдельной сборки domain/protocol.

domain нужен, чтобы protocol и simulation использовали общие значения без
зависимости игровой логики от транспорта. Сетевые DTO и модель сохранения
не заменяют внутреннюю модель мира.

## 4. Симуляция и владение состоянием

- Шаг движения T004 фиксирован и независим от FPS: 20 Гц, 0.05 секунды,
  обычная скорость 4 м/с. T009 добавляет спринт 7 м/с, нормализованную
  выносливость 0–1, расход 0.2/с и восстановление 0.1/с; истощение запрещает
  спринт до 20%. T010 добавляет Ctrl-скрытность 2 м/с с приоритетом над Shift,
  восстановлением запаса и радиусом шума 2/8/16 м для скрытности/ходьбы/спринта;
  покой и полная блокировка стеной обнуляют шум. Протокол v5 передаёт намерение
  скрытности, режим и вычисленный сервером шум всех персонажей.
  Сервер и клиентское предсказание используют один шаг. Параметры прототипа заданы в content; баланс уточняется
  после игровой проверки. stepPlayerMovement принимает явный stepSeconds,
  отклоняет несовпадение с movementStepSeconds, нормализует диагональный ввод
  и возвращает новое PlayerMovementState без мутации входов.
  В T005 Room вызывает этот шаг через управляемый Colyseus setTimestep
  с интервалом 50 мс. Каждый callback завершает ровно один фиксированный шаг;
  measured delta не меняет скорость шага. При перегрузке симуляция замедляется,
  накопленная задержка не догоняется неограниченной серией шагов.
  Локальный адаптер хранит один pending-ввод на подключение, применяет последние
  намерения на шаге и формирует отдельный ack для каждого подключения.
  Удерживаемое направление действует максимум десять шагов без свежего ввода.
  Клиент отправляет WASD до 10 Гц; T008 предсказывает своё движение
  общими правилами, согласуя его с сервером (см. MOVEMENT_PROTOCOL.md).
- Время шага передаётся явно: stepSeconds и tick. Время жизни тела — отдельная
  абсолютная отметка сервера, поскольку 24 часа означают реальные часы.
- RNG передаётся явно; генерация использует seed и версию генератора.
- Общая функция движения используется сервером и клиентским предсказанием.
  Одинакового seed недостаточно для гарантии воспроизводимости всей симуляции:
  нужны одинаковые шаг, порядок обработки, правила и состояние RNG.
- Для предсказания выбираем воспроизводимый порядок обновления сущностей.
  Точность чисел и допустимые отклонения проверяем на целевых средах.
- Идентификаторы устойчивы; игровые величины имеют явные единицы: секунды,
  координаты мира, масса. Рендер переводит координаты мира в пиксели.
- Mutable-состояние мира изменяется назначенными системами на шаге сервера.
  Контент и команды — readonly. Нет глобального изменяемого singleton мира.
- UI и сеть не меняют здоровье, владельца предмета или результат попадания напрямую.
- Столкновения — общая игровая логика. Phaser physics не является серверным
  источником правил движения и столкновений.
- Синхронный шаг не выполняет await, запросы БД, чтение файлов или сетевые вызовы.
  Адаптеры подают завершённые результаты через очередь команд следующего шага.
- Последовательность систем зафиксировать до первой реализации боя;
  события не должны случайно обрабатываться дважды из-за порядка callback.

Объекты и функции предпочитаем для правил и данных; классы используем для
жизненного цикла Scene, Room и адаптеров, где этого требует библиотека.
Наследование не является механизмом описания всех предметов или типов зомби.

## 5. Асинхронность и сеть

- Одиночный режим принимает только локального игрока на loopback. Кооператив
  включается явно; друзья подключаются в браузере к адресу компьютера хоста
  по LAN или через интернет в защищённой частной виртуальной сети.
- Сервер раздаёт собранный клиент; игровой URL определяется от origin страницы.
  Dev-сборка может использовать локальный proxy. Адрес 127.0.0.1 не зашивается
  в клиентский игровой endpoint, поскольку у друга он указывает на его компьютер.
- T005A загружает в память только index.html и JS/CSS из assets готовой сборки
  при старте; пути определяются относительно серверного модуля, независимо от cwd.
  HTTP не читает произвольные пути с диска, не выдаёт source maps и не подставляет
  HTML для отсутствующих ресурсов. GET/HEAD имеют MIME types и no-store;
  изменения сборки требуют перезапуска процесса. При отсутствии сборки запуск
  завершается до открытия порта с подсказкой выполнить npm run build.
  Статические ответы завершаются через Node HTTP end(body) перед маршрутизатором
  Colyseus с общей проверкой Host/Origin: его Response-адаптер оставлял большие
  ответы открытыми после backpressure. Игровые маршруты остаются у Colyseus.
  Production по умолчанию разрешает только origin сервера. Dev явно запускается
  с --dev, не требует dist и разрешает origin Vite. CLIENT_ORIGIN добавляет
  только проверенный HTTP origin выбранного хоста; Host и WebSocket Origin проверяются
  в обоих режимах. Доступ solo остаётся привязан к 127.0.0.1.
- T005B включает кооператив только при явном COOP_HOST: private IPv4 локального
  интерфейса, без wildcard/public/loopback адресов. Listener привязан только к нему,
  Host/Origin разрешают выбранный адрес, клиент использует origin страницы.
  Dev с COOP_HOST запрещён; собранный клиент и HTTP/WS работают в доверенной LAN.
  T005C добавляет COOP_NETWORK=tailscale: COOP_HOST обязателен и допускает только
  IPv4 диапазона 100.64.0.0/10, назначенный локальному интерфейсу. Без этого режима
  диапазон отклоняется; lan остаётся значением по умолчанию. Неверный режим
  останавливает запуск. Проверка адреса не удостоверяет VPN: оператор должен
  выбрать адрес Tailscale и настроить защищённый маршрут. Listener, Host/Origin,
  приглашения и same-origin HTTP/WS используют прежний путь без proxy.
  Инструкция и отдельная интернет-приёмка: [INTERNET_COOP.md](INTERNET_COOP.md).
  Firewall/роутер и настройки VPN приложение не меняет.
- WorldAccess создаёт 8 одноразовых приглашений на 30 минут. Они сохраняются
  в файле 0600 внутри временного каталога 0700 и удаляются при штатном shutdown.
  В журнал выводится только путь к файлу. POST /session с доверенным Origin
  атомарно погашает приглашение и выдаёт случайную HttpOnly SameSite=Strict cookie,
  имя которой включает PORT. В таблицах lookup хранятся SHA-256 digest секретов.
  Cookie проверяется до matchmaking, до WebSocket upgrade и в Room onAuth;
  onJoin получает только серверный playerId. ID из payload не даёт полномочий.
  Текущий cookie сохраняет идентичность, не погашая другое приглашение.
- До 8 персонажей и 16 соединений ограничивают ресурсы прототипа; это не результат
  нагрузочного измерения. Mutable-состояние и управление разделены по playerId,
  порядок pending-команд общий, ack относится к подключению. Вкладки одного
  участника делят управление по правилам T005; ввод другого участника не влияет
  на него. Snapshot v2 содержит своего игрока и позиции остальных, без сессий
  и приглашений. Клиент отображает подтверждённые позиции и удаляет fragment
  приглашения из истории до HTTP-входа. После disconnect персонаж останавливается
  и остаётся в мире; cookie возвращает его на ту же позицию до остановки хоста.
  Сессии, приглашения и позиции пока находятся только в памяти.
- Все участники одного процесса используют один мир; каждому назначается свой
  персонаж. Повторный вход восстанавливает участника, а не создаёт новый мир.
- Доступ друзей требует приглашения и привязки к серверной идентичности.
  Локальное размещение не отменяет проверки команд, Origin и прав на персонажа.
- Остановка, сон или недоступность хоста завершают связь со всеми клиентами;
  UI сообщает о потере хоста, мир не переносится автоматически на другой компьютер.

- Сервер проверяет форму, диапазоны, полномочия, частоту и допустимость команд.
  TypeScript не заменяет runtime-проверку сетевого JSON.
- Команда действия имеет ID; повтор после переподключения не дублирует действие.
- Изменения мира сериализованы. Сетевые callback ставят команды в очередь,
  а не обходят правила симуляции.
- Результаты загрузки чанков имеют ключ мира, координаты и версию запроса;
  устаревший результат не заменяет новый мир или состояние после переподключения.
- Ресурсы Scene/Room освобождаются: подписки, таймеры, input handlers, звук.
  Отмена и dispose — явная часть жизненного цикла.
- Потеря соединения не создаёт новый персонаж и не обходит уязвимость в бою.
- Синхронизируется область интереса, приватные данные других игроков не отправляются.
- Предсказание применяется к движению; лут, урон и выдача предметов подтверждаются сервером.

## 6. Мир и сохранение

T006 добавляет локальную камеру и прицел, перевод координат canvas в мировые
координаты и движение по клику. Клиент отправляет намерение movement-target;
протокол v3 использует общий sequence с клавиатурой. Сервер выбирает последнее
намерение и вызывает чистый stepPlayerToward из simulation с фиксированным шагом:
скорость прежняя, последний шаг ограничен расстоянием до цели. Тайм-аут ввода,
контроль соединения и остановка чужой вкладки работают по прежним правилам.
Клиентский прицел пока не отправляется серверу. Сетка рисуется только в видимой
области, без загрузки большого мира. Поиск пути отложен.

T007 хранит три статических прямоугольных препятствия в content. Клиент рисует
эту же геометрию; сервер после stepPlayerMovement/stepPlayerToward вызывает чистую
resolveMovement из simulation. Квадрат персонажа 0.7 × 0.7 м расширяет границы
препятствий; непрерывная проверка отрезка находит первый контакт и позволяет
скольжение вдоль грани. До двух контактов ограничивают обе оси без зависимости
от порядка препятствий. Начальная позиция должна быть свободна; восемь spawn
проверены тестом. Динамические препятствия и исправление проникновения не входят
в этот прототип. Столкновений между персонажами нет.

Протокол v3 не меняется: препятствия фиксированы в одной сборке клиента/сервера,
snapshot передаёт уже ограниченную сервером позицию. Клиент не использует Phaser
physics. T011 задаёт контракт процедурной геометрии ниже; T012 добавляет локальную загрузку соседей.
Цель за стеной сохраняется до новой команды или отмены ввода; обход ручной.

T008 добавляет клиентский адаптер MovementPrediction с явным локальным временем.
Он переигрывает ограниченную историю намерений от каждого snapshot, удаляет
обработанные sequence по ack и использует общую simulation со столкновениями.
Экстраполяция ограничена 500 мс; переполнение 64 записей оставляет серверную
отрисовку до нового подключения. Свой персонаж/камера используют предсказание,
остальные персонажи и UI координат — подтверждённые значения. Протокол v3
и серверные правила не меняются. Оценка задержки приближённая, коррекции прямые;
точная синхронизация часов и интерполяция других игроков отложены.

T011 добавляет чистый пакет worldgen и readonly WorldChunk/WorldChunkKey в domain.
Ключ: seed (1–128 UTF-16 code units), generatorVersion (сейчас 1), целые chunkX/chunkY
в пределах ±1 000 000. Центр чанка находится в (chunkX × 64, chunkY × 64) м;
полуоткрытые границы — центр ±32 м. Местность состоит из 1024 плиток 2 × 2 м
(grass/dirt/gravel), непроходимая геометрия — WorldObstacle в мировых координатах.
Хеш FNV-1a с отдельными каналами местности/камней зависит от всего ключа;
генерация не использует runtime API, глобальное состояние и порядок соседних запросов.
Результат глубоко заморожен. Геометрия v1 защищена контрактной SHA-256 фикстурой.

Три прежних препятствия стали шаблоном стартовых руин в content. Генератор переносит
его в центр участка и добавляет камни в угловых областях, сохраняя восемь spawn.
Край шириной 2 м всегда травяной и свободен от препятствий: стыки одинаковы
по всем четырём сторонам, включая отрицательные координаты. Это начальное правило
v1; дорог и региональной генерации пока нет. Terrain декоративный и проходимый;
столкновения используют только obstacles. ID включает версию и координаты чанка,
уникален внутри одного мира. Seed относится к ключу мира, а не к ID препятствия.

initialWorldChunk сохраняет публичный эталон начала мира: seed zombi-survive,
версия 1, координаты (0, 0). T012 добавляет чистую loadWorldChunks: на входе
позиции и предыдущее readonly-окно, на выходе объединение соседей 3 × 3.
Координата чанка — floor((метры + 32) / 64), включая отрицательные значения.
Неизменившееся окно сохраняет ссылку; общие чанки переиспользуются, дальние
не входят в результат. Ключи другого seed/версии не переиспользуются.
Глобального изменяемого кеша нет: владельцы — адаптеры приложений.

WorldTerrain клиента держит девять чанков вокруг отображаемого персонажа,
по одному Phaser Graphics на чанк. Дальние Graphics уничтожаются; disconnect
и shutdown освобождают окно. MovementPrediction отдельно держит до девяти
чанков вокруг авторитетной позиции: ореол 64 м покрывает движение и footprint
за максимум 500 мс экстраполяции. Reset удаляет ссылки. Сервер перед движением
обновляет объединение окон всех существующих персонажей: максимум 72 чанка для
восьми, пересечения не дублируются. Отключённые персонажи пока остаются в мире,
поэтому их окна сохраняются до остановки процесса. При переходе в соседнее
окно создаются только недостающие чанки; возврат воспроизводит прежнюю геометрию.

Генерация синхронная и ограниченная размером окна, без IO, await, таймеров и
поздних результатов. Впервые чанк создаётся при необходимости в адаптере шага/
отрисовки; геометрия доступна до resolveMovement. Настройка seed, worker-потоки
и передача ключей/геометрии по сети отложены. Протокол движения v5 не меняется;
клиент и сервер нужно пересобирать вместе. Генератор v1 и его фикстура неизменны.

Чанки воспроизводятся по seed, координатам и версии генератора. Крупные дороги
и поселения согласованы на уровне региона. Сохраняются изменения базового мира.
Изменение генератора не меняет уже исследованную карту без миграции.

При работающем сервере хоста время, погода и таймеры лута продолжаются без игроков.
Движение зомби рассчитывается в активных областях; область с отключённым уязвимым персонажем остаётся активной.
Остановка или сон компьютера хоста останавливает симуляцию мира. После запуска
восстанавливаются сохранённые состояния; движение, AI, погода и лут за перерыв
не симулируются. Абсолютные сроки в реальных часах проверяются при восстановлении.
Закрытие браузера хоста не останавливает отдельный серверный процесс. Уязвимость
отключившегося персонажа действует, пока мир работает; остановка всей сессии
не должна запускать новую симуляцию в браузере оставшегося участника.

Хранилище имеет самостоятельную версию схемы и миграции. Доменная модель,
сетевой DTO и запись БД разделены явными преобразованиями.
Перенос предмета и смерть — атомарные изменения. У предмета один владелец.
Критические изменения подтверждаются после устойчивой записи; перед реализацией
определить модель восстановления снимков и подтверждённых изменений.
Движение можно сохранять периодически с явно заданным допустимым окном отката.

Тело и оставшиеся вещи истекают через 24 реальных часа даже после остановки
сервера. Уже забранные вещи не удаляются. Бэкап проверяется восстановлением.

## 7. Производительность и проверки

- Профилируем время шага, память, трафик и очередь сохранения на компьютере хоста.
- Проверяем одного игрока и двух участников на разных устройствах, завершение
  хоста, повторное подключение и восстановление локального мира.
- Пространственный индекс используется для соседей, столкновений и видимости.
- AI и генерация имеют ограничение работы за шаг; дальние чанки освобождаются.
- Pooling, workers и сложные структуры вводим после измерения реальной проблемы.
- Проверяем правила отдельно от графики, а взаимодействие — интеграционными сценариями.
- Тесты используют контролируемые шаги времени и RNG; реальный sleep не задаёт исход теста.
- Проверяем повторные команды, смерть один раз, конкурирующий подбор, восстановление
  и гонки загрузки чанков. Перед увеличением вместимости проводим нагрузочные проверки.

## 8. Как менять архитектуру

Для новой зависимости пакетов, нового архитектурного слоя, движка или хранилища
создать docs/adr/NNNN-<decision>.md: проблема, варианты, решение, последствия,
путь миграции и проверка. Поддерживать небольшие изменения с понятной причиной.
Не создавать папки utils/common/managers как склад несвязанных систем.
Помощник находится рядом с системой, которой принадлежит.

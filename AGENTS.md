## Разработка

- Ручной режим: одна небольшая задача одним агентом за запуск.
  Подагенты разработки только при отдельном поручении параллельной работы.
- Менять только файлы задачи, учитывать чужие изменения, не отменять их.
- Общие конфигурации, зависимости и архитектурные контракты изменяет ведущий.
- При делегировании явно назначить владение файлами, контекст, контракты,
  проверки и применимые скиллы; напомнить, что исполнитель работает не один.
- Завершение: docs/PR_PROCESS.md, локальные проверки, отдельный PR, контроль CI.
  Слияние — по отдельному поручению. Следующая зависимая задача ждёт слияния.
- Записать результат и ограничения в docs/PROGRESS.md. Не начинать следующую задачу.

## PR-ревью: пользовательские правила

- Сравнение с origin/main; scope только frontend. Backend, сервер, миграции,
  backend-конфигурацию и backend API намеренно исключить и перечислить в Unchecked areas.
- До анализа определить цель, frontend-файлы/модули, влияние на контракты frontend,
  конфигурацию, безопасность/авторизацию, async/конкурентность и frontend-тесты.
  Неполный контекст явно отметить. При необходимости читать соседний код.
- Для явного PR-ревью запустить ровно шесть подагентов: безопасность, качество кода,
  баги, race conditions, flaky tests, поддерживаемость. Каждый проверяет только свою
  область, без дублирования. Не затронутую область явно отметить.
- Запуск без истории родителя (fork_turns: none при доступном spawn_agent);
  весь контекст передать в message: origin/main, изменённые frontend-файлы,
  область, формат findings, абсолютные пути применимых скиллов, «ничего не менять».
  Backend-файлы не передавать. Не использовать полный fork с overrides.
- Findings: Critical/High/Medium/Low, file, line/диапазон, конкретный risk,
  проблема, исправление, confidence high/medium/low, unchecked areas.
  Стиль без реального риска не включать. Не придумывать проблемы; низкую уверенность указать.
- Дождаться всех шести, объединить, убрать дубли, сгруппировать по severity.
- Итог: Context; Findings с Critical/High/Medium/Low; No issues при отсутствии
  существенных проблем («Существенных проблем не обнаружено.»); Unchecked areas;
  Review limitations: diff-based анализ, доступный runtime-контекст, скрытые зависимости,
  неполные данные о нагрузке и игровых данных. Отметить исключённый backend.
- Critical: уязвимости, утечки, обход авторизации, потеря данных из-за race,
  риск падения production. High: вероятный production-баг, breaking change,
  неправильная обработка ошибок, flaky tests. Medium: edge cases, сомнительная логика,
  читаемость с реальным риском, слабая наблюдаемость. Low: мелкие улучшения;
  косметические style-findings без риска исключены.
- Для review указанной ветки не переключать checkout по умолчанию: использовать
  локальную ветку или origin/<branch>. Если ref отсутствует/неактуален, fetch origin
  <branch> main и анализ без checkout. Checkout только если необходим и безопасен;
  при незакоммиченных изменениях предпочитать diff. Явно назвать анализируемый ref.
- При style-review применить пользовательский frontend-code-style; его открытые
  вопросы не превращать в запреты. Отдельный style-аудит только по явному запросу.
